On tested main, [`reviewFactActivityCTE`](../../../internal/infrastructure/sqlite/corrected_activity_query.go#L27) starts from effects on holdings/costs; [`listActivitiesUntilQueryMode`](../../../internal/infrastructure/sqlite/activity_repository.go#L376) then retains only activities with a `holding_quantity` effect. ## Findings, console and network

**P2: review replay drops funding but retains a buy's cash debit.** A service-seeded fresh synthetic fixture, followed by a rule created in the actual browser UI, reproduces HTTP 422 with the payload and server trace saved. On Oct 1 UTC, after an empty History Origin, the service creates a brokerage account opened that day, records a USD 2,000 contribution effective at 00:10, then buys 10 units at USD 100 with a USD 5 fee effective at 00:20. It imports a USD 100 NAV series for Oct 1–17 and builds complete closed-day snapshots. The full accepted ledger ends at USD 995 cash. The browser previews a `Meet all` rule (`Holding amount > USD 900` AND `Cost > USD 1,002`) and shows `Error: Amount: The history could not be updated.` A real `POST /wails/runtime` returns 422 with `history_update_failed` / `historical replay reached a negative balance`; captured server output contains the same error. Review capture selects activities by position/cost effect, so it filters out the cash-only contribution but retains the buy for its quantity effect. Hydration then reattaches every buy effect, including the USD 1,000 debit; replay starts from the account's zero starting cash and errors on that debit before applying the separate fee effect. This is a code-path-level cause, confirmed against the exact same synthetic activity data and not a baseline ordering or missing quote issue. Suggested fix: keep the cash replay inputs internally consistent—either replay the relevant funding effects too or exclude account-cash effects before the review-only money replay—and add a regression for a contribution followed by a fee-bearing buy.

**Low severity (P3): missing favicon.** Each new page requested `GET /favicon.ico`, which returned 404 and produced a Chromium console error. The UI otherwise loaded and operated; successful browser flows had no unexpected API failures or page exceptions. Suggested fix: serve the app icon at `/favicon.ico` or remove the request if the HTTP server does not provide one.

**P3, browser-mode navigation gap: browser Back/Forward does not restore SPA views.** After opening Return Analysis with an account filter and using app navigation to open Asset Changes, browser Back left the app at `about:blank`. Forward reopened `/` at Overview. The routes all remained at `/`, so browser history did not capture the in-app route or selected filters. The in-app Back path did restore its tested analysis context. Suggested fix if browser-mode Back/Forward is a supported flow: record route changes in browser history and restore the route/filter state on Back/Forward. This observation applies to the HTTP/browser workflow; native Wails window navigation was not run.

Other observed HTTP 422 responses were expected validation/precondition paths: zero-value preview, negative manual quote, missing History on the review fixture before starting it, archiving an instrument with a holding, and attempting an earlier History Origin with already-present holdings. Each displayed an error state. The held-instrument archive conflict and earlier-origin conflict are not reported as product defects. The contribution→buy review-preview 422 is unexpected and is the P2 defect above. The focused reproduction had no page exceptions, one unexpected review-preview 422, and one favicon 404; other UI validation sweeps intentionally produced their recorded 422 responses. Browser sandboxing was disabled due to the launch blocker documented above.
