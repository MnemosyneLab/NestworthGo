# v0.1.3 Implementation Review — 2026-08-23

## Review conclusion

The v0.1.3 implementation establishes useful foundations: schema 4 migrates
cleanly in the automated fixtures, Activities and typed effects are separated
from Fyne presentation, Undo/Fix are append-only application operations, and
the full test, race, vet, formatting, and build gates pass. The review still
found **11 open issues**: **5 High** and **6 Medium**.

The highest-risk problems are:

1. a debt payment with interest or a fee leaves the current cash balance
   without the principal deduction;
2. historical valuation starts from today's portfolio objects and does not
   apply effective state/preference observations, so present state can rewrite
   earlier days;
3. normal Account/archive/source-preference edits do not create the effective
   observations required by the historical model;
4. Record Change accepts archived Accounts and Holdings; and
5. the shipped History UI exposes only Money added, leaving most of the
   v0.1.3 family workflows inaccessible.

This document is findings-only. No implementation code was changed as part of
this review.

## Detailed findings

### V013-01 — Debt payment with interest/fee drops the principal deduction

**Severity:** High

**Evidence**

- `internal/domain/change.go:1071-1078` calculates a cash result after removing
  principal.
- `internal/domain/change.go:1083-1091` calculates the fee from the original
  `ChangeState`, not from that principal-adjusted result, and then replaces
  `cashView` with the fee-only result.
- `internal/infrastructure/sqlite/change_repository.go:75-107` writes the one
  returned endpoint view for every cash effect on that Account/currency.
- `internal/domain/change.go:1031-1048` and `:1060-1094` do not require the cash
  Account to be a non-liability Account or to differ from the debt Account.

**Failure example**

With cash `1,000`, debt principal `100`, and fee `10`, the preview contains
principal and fee effects but returns cash `990`, not `890`. Commit therefore
projects `990` as the current cash value. Historical effect replay later removes
both `100` and `10`, so current and historical state also disagree. If the same
Account is supplied as both debt and cash, current projection and effect replay
can diverge for debt draw/payment even without a fee.

**Recommended correction**

- Apply fee/interest to the cash result after principal, using one cumulative
  endpoint result.
- Require distinct debt and cash Account IDs.
- Require the debt endpoint to be a liability and the cash endpoint to be an
  allowed non-liability Balance or Holdings-cash Account.
- Keep validation, preview, effects, and projection construction in one domain
  operation.

**Required regression tests**

- Balance cash and Holdings cash with principal plus fee;
- exact preview, persisted current cash, debt balance, and historical replay
  all equal the same expected result;
- insufficient cash for principal plus fee writes nothing; and
- same Account, liability-as-cash, mismatched currency, zero, and negative
  inputs are rejected before persistence.

### V013-02 — Historical reconstruction leaks present state into earlier days

**Severity:** High

**Evidence**

- `internal/application/historical_snapshot.go:117-129` begins with the current
  `ReadPortfolioSnapshot(IncludeArchived: true)` and separately loads only
  origin components and Activities.
- `internal/application/historical_snapshot.go:178-194` replaces an Account
  value or Holding quantity only when the reconstructed maps contain that ID.
  Otherwise the current `LatestValue` or current quantity remains in place.
- The same function never reads `account_state_observations`,
  `instrument_preference_observations`, or `fx_preference_observations`.
- `internal/application/historical_snapshot.go:212-240` uses current Instrument
  metadata and the current FX preference row. Filtering the current row by
  `UpdatedAt` cannot recover the preference that was effective before a later
  update.

**Impact**

- An Account or Holding created after a historical cutoff can appear on the
  earlier day with its current value/quantity.
- Archiving an Account today can remove it from all earlier valuations; an
  inclusion/Ownership/source change today can be applied to earlier days.
- A changed FX preference may disappear from an earlier day instead of falling
  back to its previous effective value.

This violates the locked rule that historical calculation is Starting point
plus Activities and effective observations through the cutoff, never current
metadata copied backward.

**Recommended correction**

Build an explicit as-of portfolio model. Include only entities that existed at
the origin or were introduced by an effective post-origin event, initialize
unseen value/quantity endpoints to absent/zero instead of retaining current
projections, and select the latest state/Ownership/preference observation by
`effective_at`, `created_at`, and ID at or before the cutoff.

**Required regression tests**

- Account/Holding created after the requested day;
- Account/Holding/Instrument archived after the requested day;
- include-in-net-worth and Ownership changed across two closed days;
- Instrument and FX source changed twice, proving the older preference remains
  effective for the older cutoff; and
- rebuilding the same day after current metadata changes either stays
  byte-equivalent or appends exactly the expected corrected revision.

### V013-03 — Effective observations are disconnected from normal mutations

**Severity:** High

**Evidence**

- `internal/application/service.go:769-773` updates Account metadata and
  Ownership directly, and `internal/application/service.go:839-847` archives an
  Account directly.
- `internal/application/portfolio.go:101-109`, `:126-138`, and `:406-436`
  directly archive Instruments or update Instrument/FX source preferences.
- The append services exist at `internal/application/history_changes.go:135-192`,
  but production mutation paths do not call them.
- The only application call sites found for those append methods are the direct
  row-count checks in `internal/application/change_service_test.go:321-372`.

**Impact**

After History starts, ordinary settings dialogs can change valuation-relevant
state without recording when that state became effective and without marking
the affected closed date dirty. Even after the historical reader is corrected,
there will be no observation evidence from which to reconstruct those edits.

**Recommended correction**

For every valuation-relevant metadata mutation, atomically update current state,
append the matching effective observation, and mark the earliest affected
closed day dirty. Make the public append methods internal orchestration details
unless there is a genuine external caller that can supply a fully validated
observation.

**Required regression tests**

- Account archive/unarchive, inclusion flags, and Ownership update;
- Instrument archive/source and FX source update;
- current row, effective observation, and dirty marker commit together or all
  roll back; and
- metadata-only edits that do not affect valuation do not create false history
  work.

### V013-04 — Record Change accepts archived endpoints

**Severity:** High

**Evidence**

- `internal/application/change_service.go:17-45` intentionally loads archived
  objects and adds every Account and Holding to `ChangeState` without checking
  Account, Holding, parent Account, or Instrument archive state.
- The change-domain state types contain no archive flag, so command builders
  cannot reject these targets.
- `internal/infrastructure/sqlite/change_repository.go:83-114` verifies Account
  ownership/tracking mode or updates a Holding by ID, but does not require the
  endpoint and its parents to remain active inside the commit transaction.
- Existing archived-write coverage in
  `internal/infrastructure/sqlite/repository_test.go:295-328` exercises the old
  direct repository methods, not `CommitActivity`.

**Impact**

An application/API caller can record money, transfer, trade, debt, or quantity
effects against objects that the family has archived. The Activity remains in
the audit trail while current valuation may hide the affected endpoint.

**Recommended correction**

Exclude archived endpoints from `ChangeState`, return stable target-specific
errors, and revalidate Account/Holding/Instrument active state in the same
SQLite transaction that inserts the Activity. The transaction check is needed
to close the preview-to-commit archive race.

**Required regression tests**

- each command family against an archived Account;
- transfer/trade against an archived Holding, parent Account, or Instrument;
- archive between preview and commit; and
- rejection leaves Activities, effects, and all projections unchanged.

### V013-05 — The History UI exposes only one change workflow

**Severity:** High

**Evidence**

- `internal/ui/history_page.go:42-91` always constructs
  `domain.MoneyAddedInput` with only Account, amount, and reason.
- There is no UI choice or friendly form for Money removed, cash transfer,
  investment transfer, Buy/Sell, value update, debt draw, or debt payment.
- `internal/ui/history_page.go:105-128` loads a fixed 100 entries and exposes
  only Undo. It has no Fix entry, detail view, Starting point marker, Account /
  change-type / date filters, or keyset paging.
- `internal/ui/analytics_page.go:14-65` provides a text list only; the History
  page does not offer the contract's Timeline and Net worth views, and Overview
  has no compact trend integration.
- No v0.1.3 History/Analytics workflow test exists under `internal/ui`.

**Impact**

Most of the domain implementation cannot be reached by a normal family user.
The release evidence labels the History page and net-worth experience shipped,
but the application only supports one inflow form and a minimal list.

**Recommended correction**

Implement one family-facing change picker with the seven locked choices and
type-specific forms, all routed through Preview/Record Change. Add optional
local date/time and note, friendly details, Fix entry, filters/pagination,
Starting point, missing-value action, and the Timeline/Net worth navigation
described by the release contract. Keep Activity/effect vocabulary out of the
UI.

**Required regression tests**

- Fyne construction and interaction coverage for all seven choices;
- preview and save use identical typed inputs and no calculation is duplicated
  in UI code;
- Undo/Fix, filters, pagination, Starting point, and incomplete-value action;
  and
- English, Simplified Chinese, keyboard focus, and accessible labels for every
  new control.

### V013-06 — Post-History non-zero creation has no usable workflow

**Severity:** Medium

**Evidence**

- `internal/application/service.go:545-551` rejects creation of an Account with
  a non-zero initial value once History exists and tells the caller to record a
  change before creating the Account.
- `internal/application/portfolio.go:196-200` does the same for a non-zero
  Holding.
- A change cannot target the not-yet-created Account or Holding, so the error's
  requested ordering is impossible.
- `v0.1.3-technical-design.md:168-171` requires a simple “already existed or
  new money” explanation and an explicit reconciliation/inflow Activity.

**Impact**

After enabling History, the ordinary create form fails for a new bank,
investment, or debt position with an initial amount. A knowledgeable user can
create zero first and then record a separate change, but the promised simple
family workflow is absent and the error does not explain that workaround.

**Recommended correction**

Create the zero-valued entity and its chosen reconciliation/inflow Activity in
one application transaction, or expose a guided two-step operation whose first
step safely creates the ID and whose second step is recoverable/idempotent.
Prefer the atomic operation so a failed Activity cannot leave a misleading
empty Account/Holding.

**Required regression tests**

- “already existed” and “new money” for Account and Holding creation;
- transaction rollback at every insert boundary;
- zero start creates no Activity; and
- UI wording contains no ledger terminology.

### V013-07 — One completed date clears the whole dirty interval

**Severity:** Medium

**Evidence**

- `internal/application/historical_snapshot.go:110-112` calls
  `MarkDailySnapshotCompleted` after each individual date.
- `internal/infrastructure/sqlite/snapshot_repository.go:54-59` sets
  `dirty_from` to `NULL` whenever the completed date is on or after the earliest
  dirty date.

**Failure example**

If `dirty_from` is January 1 and January 1 completes, the row becomes clean even
though January 2 through yesterday have not been rebuilt. A cancellation or
failure immediately after that write loses the persisted resume boundary.

**Recommended correction**

Persist a next-unprocessed date after each successful day, or clear
`dirty_from` only after the requested closed-day target has completed. Update
the progress cursor and `last_completed_closed_on` under an explicit batch
contract that distinguishes initial catch-up from a dirty-range rebuild.

**Required regression tests**

- cancellation after the first and a middle day;
- failure after a successfully saved incomplete snapshot;
- an earlier dirty change arriving during rebuild; and
- restart resumes without a hole and clears dirty state only after the final
  affected closed day.

### V013-08 — Backdated manual quotes do not mark history dirty

**Severity:** Medium

**Evidence**

- `internal/application/portfolio.go:369-399` appends a dated Instrument quote
  and selects Manual without touching `history_snapshot_state`.
- `internal/application/portfolio.go:450-484` does the same for a dated FX
  quote.
- History dirty marking is implemented for Activities and explicit observation
  append methods only.
- The product contract explicitly includes a dated quote among changes that
  schedule historical maintenance.

**Impact**

A family member can add the missing price or FX rate for a closed day while the
cached trend remains partial/stale. The current worker's full rebuild can mask
this after a later page navigation, but there is no correct persisted pending
signal and a future dirty-range worker would skip the change entirely.

**Recommended correction**

Append the quote, update the selected source where applicable, and mark the
quote's earliest affected closed local date dirty in one transaction when
History exists. A quote for today must not create false closed-day work.

**Required regression tests**

- backdated Instrument and direct/inverse FX quote;
- a quote that changes a complete value and one that completes a partial day;
- today and future-invalid quote behavior; and
- transaction failure leaves neither quote nor dirty marker partially written.

### V013-09 — Snapshot worker always rebuilds the full history

**Severity:** Medium

**Evidence**

- `internal/ui/snapshot_worker.go:15-28` derives the start from History origin
  and the end from yesterday. It never reads `dirty_from` or
  `last_completed_closed_on`.
- `internal/ui/snapshot_worker.go:40-54` repeats 31-day batches from that origin
  on every start.
- `internal/application/historical_snapshot.go:212-221` loads complete quote
  histories per Instrument for every rebuilt day, multiplying the cost as the
  Household history grows.
- `internal/ui/snapshot_worker.go:75-84` discards cancellation state; the next
  start again begins at the origin.

**Impact**

Opening History or Analytics for a multi-year household repeatedly recomputes
every closed day even when nothing changed. Cancellation and retry provide no
work reduction. This can make an otherwise simple local family timeline feel
permanently busy and increases SQLite reads roughly with days times
Instruments/quotes.

**Recommended correction**

Expose a read model for persisted snapshot state, begin at the earlier of the
real dirty boundary and missing-catch-up boundary, stop when clean, and resume
from the persisted next date. Query all data required for a 31-day batch once
instead of loading full quote histories per Instrument/day.

**Required regression tests**

- clean history starts no worker;
- one backdated change rebuilds only the affected range;
- cancellation/re-entry resumes at the next date;
- query-bound assertion for a 31-day multi-Instrument batch; and
- current Overview/editing stays responsive during a long rebuild.

### V013-10 — Snapshot provenance and content identity are incomplete

**Severity:** Medium

**Evidence**

- Schema storage supports Holding, quote, FX quote, state-observation, and
  preference-observation IDs in
  `internal/infrastructure/sqlite/snapshot_repository.go:38-49`.
- `internal/application/historical_snapshot.go:79-92` populates Account and
  optional Instrument plus numeric values only. It never sets Holding, quote,
  FX quote, state-observation, or preference-observation IDs.
- `internal/application/historical_snapshot.go:284-299` hashes Account ID,
  amounts/currencies, and completeness, but omits Holding/Instrument identity,
  evidence IDs, and missing reason.

**Impact**

The stored revision cannot explain which quote/preference/state evidence
produced a value. A component can move between Holdings/Instruments or change
evidence while preserving the same numeric amount and content hash, causing
`SaveDailyValuationSnapshot` to skip the revision even though its contracted
content changed.

**Recommended correction**

Carry selected evidence IDs through the valuation result into each snapshot
item. Canonically sort and hash every persisted semantic field, including
component identity, native/base currency and amount, evidence IDs,
completeness, and missing reason. Do not include newly generated snapshot/item
IDs in the hash.

**Required regression tests**

- same value from a different quote/FX/preference/state observation;
- same Account total redistributed between two Holdings/Instruments;
- missing reason changes with the same subtotal; and
- identical semantic input skips a revision regardless of slice order.

### V013-11 — History surfaces bypass localization and expose internal enums

**Severity:** Medium

**Evidence**

- `internal/ui/history_page.go:43-45` displays raw reason enum values.
- `internal/ui/history_page.go:76` displays the domain's hard-coded English
  preview sentence, and `:119-120` displays raw Activity kind/reason values.
- `internal/ui/analytics_page.go:27-49` hard-codes English range and
  `complete`/`partial` labels.
- `internal/ui/snapshot_worker.go:36` and `:90-94` hard-code English worker and
  result text.

**Impact**

Simplified/Traditional Chinese users receive a mixed-language History
experience containing implementation vocabulary such as `cash_in`,
`contribution_or_gift`, and `debt_payment`. This conflicts with the release's
family-first language and paired English/Simplified Chinese requirement.

**Recommended correction**

Keep typed enum values as internal keys and map them through localized
family-facing labels. Return structured preview data rather than a final
English sentence, or localize sentences at a presentation boundary with typed
parameters. Localize progress, completeness, range labels, buttons, and
accessible descriptions.

**Required regression tests**

- English and Simplified Chinese golden labels for every Activity kind/reason;
- no raw enum strings or UUIDs in rendered History/Analytics text;
- localized preview/result sentences with formatted money/quantity; and
- worker pending/complete/partial/failure/retry accessible text.
