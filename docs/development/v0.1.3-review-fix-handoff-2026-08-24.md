## Required outcomes

Complete the work in the following order because later historical and UI tests
depend on the corrected domain contracts.

### 1. Correct Debt draw endpoint validation

**Priority:** P1

**Problem**

`internal/domain/change.go:1078-1104` validates the debt Account but still
allows the cash endpoint to be another liability or the same Account. If both
IDs are equal, current projection records one increase while historical replay
applies two additive effects.

**Implementation contract**

- Debt and cash Account IDs must differ.
- Debt must be a liability Account.
- Cash must be a non-liability Balance Account or Holdings Account cash
  endpoint.
- Principal currency must match the selected cash endpoint.
- Preview, persisted current projection, and historical replay must produce the
  same balances.
- Reuse one shared debt-endpoint validator for Debt draw and Debt payment so
  their rules cannot drift again.

**Regression tests**

- Reject identical debt/cash IDs without writing an Activity or projection.
- Reject a second liability as the cash Account.
- Accept valid Balance and Holdings cash endpoints.
- Assert exact current debt/cash values and reconstructed values after a valid
  draw.

### 2. Add creation-time historical baselines for post-origin entities

**Priority:** P1

**Problem**

`historicalPortfolioSnapshot` now filters entities by `CreatedAt`, but an
Account or Instrument created after History starts has no creation-time state
or preference baseline. Before its first later observation, reconstruction
falls back to current metadata and can copy a later Ownership, inclusion, or
quote-source change backward.

**Implementation contract**

- Creating an Account after History starts must atomically persist its initial
  Account state and Ownership observation at the creation effective time.
- Creating an Instrument after History starts must atomically persist its
  initial source-preference observation.
- A non-zero Account/Holding creation transaction must include the entity,
  creation baseline, initial Activity/effects, projections, and dirty marker in
  one transaction.
- Historical reconstruction must never use current Ownership or source
  preference as a fallback for a post-origin entity.
- A cutoff before entity creation excludes it; a cutoff after creation and
  before its first edit uses the creation baseline.

**Regression tests**

- Create an Account after origin, update Ownership/inclusion later, and verify
  both sides of the update cutoff.
- Create an Instrument after origin, change source later, and verify both sides
  of the source-change cutoff.
- Inject failure at the Activity/observation boundary and prove no partial
  entity remains.

### 3. Make archive intervals reconstructable

**Priority:** P1

**Problem**

Account archive uses effective observations, but Instrument and Holding archive
paths only update the mutable `archived_at` column and mark history dirty. After
archive then unarchive, the former interval is lost. Rebuilding the same closed
day before and after unarchive can therefore produce different results from the
same financial facts.

**Implementation contract**

- Persist append-only effective archive state for Instrument and Holding, or
  introduce an equivalent versioned state model that can represent multiple
  archive/unarchive intervals.
- Archive mutation, state observation, and dirty marker must be atomic.
- Historical reconstruction selects state by `effective_at`, then
  `created_at`, then stable ID.
- An archived Instrument must not erase an active retained Holding contrary to
  the existing v0.1.3 rule; define and test the precise valuation behavior.

If schema 4 cannot represent these observations, add a forward-only schema 5
migration. Do not silently alter an already released schema-4 definition.

**Regression tests**

- Active → archived → active intervals for an Instrument and zero-quantity
  Holding.
- Rebuild dates before, during, and after the archive interval.
- Rebuilding after unarchive preserves the same prior revisions/content.
- Failed state-observation insert rolls back the mutable archive update.

### 4. Bound backdated quote history work to the Starting point

**Priority:** P1

**Problem**

Manual quote persistence records `quoted_at` directly as both the dirty date and
the effective Manual preference date. A quote saved after History starts but
dated before the Starting point can set `dirty_from` before the origin. The
worker then requests an invalid pre-origin snapshot and repeatedly fails.

**Implementation contract**

- Quotes older than the Starting point may remain valid quote evidence if the
  current portfolio rules allow them.
- They must not schedule a snapshot before the Starting point.
- Clamp the earliest dirty date to the origin local date, or skip history work
  when the quote cannot affect any supported snapshot.
- Do not create a preference observation before the origin. Choose and test one
  explicit rule: clamp the effective preference time to the origin, or make the
  preference effective when the user saved/selected Manual while retaining the
  old quote's own `quoted_at`.
- Apply the same rule to Instrument and FX manual quotes.

**Regression tests**

- Manual Instrument/FX quote before origin, on the origin date, on a closed
  post-origin date, and today.
- `dirty_from` never precedes the origin local date.
- The worker completes instead of entering a repeatable pre-origin failure.
- Quote, preference observation, and dirty marker remain atomic.

### 5. Replace the current Fix button with a real correction workflow

**Priority:** P2

**Problem**

`internal/ui/history_page.go:367-394` immediately calls `FixChange` using the
original cash amount/reason and `time.Now()`. The user cannot change anything;
the button only appends correction evidence. Other Activity types report that
Fix is unavailable.

**Implementation contract**

- Fix opens the original family-facing form populated from the selected
  Activity and its details/effects.
- Nothing is written until the user changes or confirms the corrected values.
- On submit, call the existing atomic `FixChange` exactly once.
- Support every user-facing v0.1.3 change type, or hide/disable Fix with a clear
  explanation for types not yet safely reconstructable. Do not present an
  enabled button that writes an unchanged replacement.
- Preserve the original note/effective time as form defaults; allow the user to
  correct them within the normal time rules.

**Regression tests**

- Opening and cancelling Fix writes nothing.
- Correcting amount, Account/Holding, date, reason, fee, or note produces the
  expected inverse plus replacement.
- Unsupported/reversal/already-corrected entries cannot invoke a write.
- Fyne tests cover populated controls, cancellation, validation, and one
  successful correction for each supported form family.

### 6. Correct Timeline filtering and pagination

**Priority:** P2

**Problem**

The UI stores grouped keys such as `money_added`, `trade`, and `debt`, then
compares them directly with persisted kinds such as `cash_in`, `buy`, and
`debt_payment`. Most filters therefore show an empty Timeline. Pagination also
increases a numeric limit rather than using the keyset contract and breaks once
the repository's 500-row cap is exceeded.

**Implementation contract**

- Define one explicit mapping from each family filter to its Activity kinds:
  - Money added → `cash_in`
  - Money removed → `cash_out`
  - Cash transfer → `cash_transfer`
  - Investment transfer → `position_transfer`
  - Buy / sell → `buy`, `sell`
  - Value update → `value_update`
  - Debt → `debt_draw`, `debt_payment`
- Keep record-form selection state separate from Timeline filter state.
- Move Account/type/date filtering and keyset pagination to the application /
  repository query boundary; do not repeatedly fetch a larger prefix and filter
  it in Fyne.
- Preserve deterministic `effective_at`, `created_at`, ID ordering.

**Regression tests**

- Every grouped filter returns both its expected variants and no unrelated
  types.
- Account plus type plus date filters compose correctly.
- More than 500 Activities can be traversed without duplicates, gaps, or
  returning to the first page.
- Changing a Timeline filter does not change the Record change form type.

### 7. Finish the family-facing form and localization boundary

**Priority:** P2

**Problem**

The History page exposes every possible field at once regardless of change
type, making the form harder to understand. Preview still renders the domain's
hard-coded English `Sentence`, so Chinese users receive mixed-language output.
The date input also fixes time at noon and does not implement the optional local
time contract.

**Implementation contract**

- Render only the controls required by the selected family change type.
- Same-currency transfer asks for one amount; cross-currency transfer asks for
  Sent and Received.
- Debt draw does not display fee; debt payment may display optional interest or
  fee.
- Provide optional local date and time with DST-gap/overlap validation through
  `ResolveLocalDateTime`.
- Replace final English domain sentences with structured preview data or a
  typed localization key plus parameters. Fyne owns localized wording; Go owns
  financial calculation.
- English, Simplified Chinese, and Traditional Chinese must not expose raw enum
  values or UUIDs.

**Regression tests**

- Per-type visible/hidden control tests.
- Localized preview goldens for every command family.
- Date/time tests for normal time, DST gap, and DST overlap.
- Keyboard focus and accessible labels for dynamically changing forms.

### 8. Persist complete snapshot preference provenance

**Priority:** P2

**Problem**

Valuation now carries `FXPreferenceObservationID`, but
`DailyValuationSnapshotItem` and snapshot persistence only retain the
Instrument preference observation. The FX preference ID is dropped and omitted
from the content hash.

**Implementation contract**

- Add a distinct nullable FX-preference observation ID to the snapshot item
  model and storage.
- Persist and hash Instrument preference and FX preference independently.
- Add foreign keys/index verification where compatible with the schema
  migration policy.
- A change in selected FX preference evidence must append a new revision even
  when the resulting numeric value is unchanged.

This likely requires a forward schema migration; do not overload the existing
Instrument preference column with two ID types.

**Regression tests**

- Same native/base value produced under two FX preference observations creates
  different hashes and revisions.
- Readback retains quote, FX quote, Account state, Instrument preference, and FX
  preference evidence IDs.
- Identical semantic input in a different slice order still skips a revision.

### 9. Make snapshot batches bounded and internally consistent

**Priority:** P2

**Problem**

The worker now respects persisted progress and caches quote histories, but each
day still reloads the portfolio, origin data, all observations, all Activities,
and Activity effects. The batch is neither query-bounded nor one consistent
read snapshot, and cost grows with days times accumulated history.

**Implementation contract**

- Load one immutable batch input under one consistent SQLite read transaction:
  origin, relevant entity metadata, observations, Activities/effects, and quote
  candidates through the batch end cutoff.
- Replay that in-memory input incrementally across at most 31 closed days.
- Keep one short write transaction per completed day.
- Preserve the current dirty cursor rules when a concurrent earlier change is
  recorded during a batch.
- Cancellation remains possible between days and resumes from the persisted
  next date without gaps.
- A visible failed state provides an explicit localized Retry action.

**Regression tests**

- Query-count bound for a 31-day batch with multiple Accounts, Holdings,
  observations, quotes, and Activities.
- Concurrent backdated change during rebuild remains dirty and is rebuilt on
  the next pass.
- Cancellation after first/middle day resumes at the next unprocessed date.
- Concurrent writes do not produce a batch containing mutually inconsistent
  source/preference snapshots.
- Retry starts from persisted state rather than the origin.

## UI/product constraint

Nestworth is a family application, not a professional accounting product.
Keep the implementation vocabulary internal:

- say Account, Holding, Money added/removed, Transfer, Buy/Sell, Borrow/Repay,
  Undo, and Fix;
- do not show Activity, effect, leg, debit/credit, reconciliation group, cursor,
  dirty date, revision ID, or raw enum names;
- use one question per decision and reveal additional fields only when needed.

## Explicit non-goals

Do not add tax lots, cost basis, performance attribution, budgets, imports,
provider history backfill, background work while the app is closed, sync, or a
raw journal editor. Do not launch provider refresh from historical rebuild.
