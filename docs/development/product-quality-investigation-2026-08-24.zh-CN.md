# Nestworth 产品体验与架构问题调查及解决方案

> 调查日期：2026-08-24  
> 当前版本：v0.1.4  
> 文档状态：调查完成，待实施  
> 适用仓库：`Nestworth-go`

## 1. 文档目的

本文整理当前 Nestworth-go 在数据兼容、账户与投资建模、市场数据、窗口状态和 UI 交互方面的已知问题，供后续开发人员直接拆分任务、设计实现和验收。

本文描述的是当前代码现状和建议目标，不表示相关功能已经实现。除非特别说明，建议的网络刷新仍应由用户明确触发；页面展示应优先读取本地 SQLite 数据。

## 2. 总体结论

当前主要问题不是单一视觉缺陷，而是以下几类问题叠加：

1. 数据库仍承担从旧 schema 逐代迁移的兼容责任，与“当前版本作为破坏性更新”的目标不一致。
2. 多个表单使用具有业务影响的自动默认值，日期、币种和数据回填规则也不统一。
3. 多币种现金的底层模型已经基本具备，但用户操作流程尚未完整支持券商账户内换汇、任意币种入金/出金等场景。
4. 投资标的和汇率被隐藏在账户页弹窗中，当前值和本地历史行情缺少正式展示入口。
5. 窗口尺寸只保存、不恢复；部分固定网格、横向布局和不换行文本会撑宽卡片或页面。
6. 数量为 0 的持仓可以创建，但首次买入一个尚未持有的标的必须先手工创建零持仓。
7. FX 默认 provider 仍是 Yahoo Finance，而不是 Frankfurter。

建议优先处理数据代际边界和财务工作流，再统一市场数据页面和 UI 规范。

## 3. 问题清单与解决方案

### 3.1 移除旧版本及旧数据兼容逻辑

**优先级：P0**

#### 问题

产品计划将当前版本作为破坏性更新，只保留最新数据结构和业务逻辑，但当前启动流程仍支持从旧 schema 逐代迁移。

#### 当前现状

- `internal/infrastructure/sqlite/database.go` 同时嵌入 `schema.sql`、`schema3.sql`、`schema4.sql`、`schema5.sql` 和 `schema6.sql`。
- 新数据库也会先创建旧 schema，再顺序执行迁移到 schema 6。
- 旧数据库升级包含迁移前快照、schema 6 成本基础回填以及 `StatusMigrated` 等状态。
- `schema6_migration.go` 专门为旧数据补齐成本基础。
- `validateStoredHistoryOriginComponent` 允许读取缺少 `unit_cost` 的旧 starting point。
- `projection_kind` 仍使用 `legacy` 作为默认值和允许值之一。
- 仓库保留多代旧 schema fixture、兼容性测试和部分仅用于源码兼容的 alias，例如 `PageActivity`、`ParseFXRate` 和 `LocalDate`。

数据库完整性验证、外键验证和阻止未来版本数据库被旧程序打开，不属于旧版本兼容逻辑，仍有保留价值。

#### 解决方案

1. 新建一份完整的当前 schema，空数据库一次性创建最终结构，不再执行逐代迁移。
2. 非空数据库只接受当前 generation/schema；发现旧 schema 时返回明确的“不支持旧数据库”错误。
3. 不要静默删除旧数据库。提供以下任一安全路径：
   - 使用新的数据库文件名或新的数据 generation；或
   - 启动错误页提供“备份旧数据库并重置”操作。
4. 删除旧迁移 SQL、`schema6_migration.go`、迁移前快照逻辑、迁移状态和对应兼容 fixture/测试。
5. 将当前初始数据语义由 `legacy` 改为 `baseline`，并让所有写入显式指定 `baseline`、`event` 或 `replay`。
6. 删除对缺少成本基础等旧数据形态的读取放行。
7. 删除没有当前调用需求、只为旧源码保留的 alias 和过时版本文案。
8. settings 如果也采用破坏性更新，应提升 settings schema；旧版本 settings 直接回到最新默认值。

#### 验收标准

- 空数据库直接创建唯一的最新 schema。
- 旧 schema 数据库不会被迁移或部分写入。
- 旧数据库被拒绝时有可理解、可恢复的用户提示。
- 当前 schema 不再包含 `legacy` 数据语义。
- 仓库不再包含用于 schema 1～5 升级的生产迁移代码。
- `DB.Verify`、外键检查、完整性检查和未来 schema 防护仍然存在。

### 3.2 表单默认值、回填、日期和交互逻辑粗糙

**优先级：P0/P1**

#### 问题

多个表单会自动选择账户、成员、持仓或投资标的；不同页面对空日期和当前时间的解释不一致；币种普遍使用自由文本输入。这些行为容易让用户在未注意时提交错误数据。

#### 当前现状

- 创建账户默认选择第一个家庭成员作为 owner。
- 历史记录表单默认选择第一个账户、第二个目标账户和第一个持仓。
- 新建持仓默认选择第一个投资标的。
- 创建已有历史的持仓时，会把当前市场价自动回填为平均成本。
- 创建账户默认使用现金类/银行账户/余额跟踪，但分类变化后的 inclusion flags 不会同步表达推荐值。
- 编辑账户可以修改主分类，但 tracking mode 被锁定；修改到不兼容分类后通常只能在提交时看到错误。
- 账户、现金、投资标的等币种字段使用自由文本 Entry。
- 账户日期使用 Fyne `DateEntry`，历史记录使用纯文本 `YYYY-MM-DD` 和 `HH:MM`。
- settings 中的日期格式和周起始日没有真正接入日期输入控件。
- 空日期在不同接口中可能表示未填写、当前时刻或 UTC 当日零点。
- 当前后端表单在保存失败后会保留输入并显示行内错误，这一行为是正确的，应继续保留。

#### 解决方案

建立统一的表单与默认值规范：

1. 不自动选择会产生财务影响的实体。账户、持仓、标的和目标账户初始应为空，并要求用户明确选择。
2. 只有完全无歧义的默认值才可自动填写，例如家庭只有一个成员时可建议 owner，但仍应清楚展示。
3. 平均成本默认留空。提供显式的“使用当前价格”按钮，不要无提示回填市场价。
4. 为常用货币提供可搜索选择器，底层仍使用规范化 ISO 4217 三字代码。
5. 建立统一日期/时间组件：
   - 显示格式遵循 settings；
   - 存储仍使用 ISO 日期或 UTC 时间戳；
   - 明确标注时区；
   - “现在”“今天”“未知”必须有不同语义和视觉反馈。
6. 日期为空时不得在不同业务中隐式解释成不同时间。需要当前时间的表单应显式预填当前日期和时间。
7. 分类变化时立即更新或校验 secondary category、tracking mode 和 inclusion flags；不允许用户进入必然提交失败的组合。
8. create/edit 使用相同的字段定义、选项来源、验证和数据回填函数。
9. 对金额、数量、价格和汇率提供字段级帮助、币种后缀和即时验证。

#### 验收标准

- 表单不会静默选择错误账户、标的或持仓。
- 任何自动回填的财务值都有明确来源和用户动作。
- 日期显示、解析、时区和空值语义在所有页面一致。
- settings 的日期格式和周起始日对输入控件生效。
- create/edit 的同类字段行为一致。
- 后端失败时弹窗保持打开，用户输入不丢失。

### 3.3 券商账户支持多币种现金

**优先级：P0**

#### 问题

券商账户需要一个基础币种，同时允许持有多种现金。例如 MooMoo SG 以 SGD 为基础币种，但账户中可以同时持有 SGD 和 USD，并在账户内进行换汇。

#### 当前现状

底层已经部分支持：

- `account_cash_values` 的每条记录都有独立币种。
- `ChangeState.Cash` 的结构是“账户 → 币种 → 金额”。
- SQLite 和估值会按币种分别选取最新余额并转换到家庭基础币种。
- 账户详情会按币种显示最新现金余额。

当前缺口：

- 添加现金表单默认使用家庭基础币种，而不是券商账户的基础币种。
- 历史页的入金/出金金额仍绑定账户 `DefaultCurrency`。
- 跨账户现金转账按两个账户的基础币种判断，不能自由选择实际转出的现金币种。
- 不支持同一账户内 SGD→USD 等换汇活动。
- 没有清晰区分账户基础币种、现金余额币种和投资标的报价币种。

#### 解决方案

1. 保留 `Account.DefaultCurrency`，但只把它定义为账户展示和默认输入币种，不作为现金币种限制。
2. 所有 Holdings/券商账户的入金、出金和转账表单增加明确的现金币种选择。
3. 添加正式的 `FXConversion` 活动：
   - 同一个券商账户；
   - 输入卖出币种及金额；
   - 输入买入币种及金额；
   - 可选费用和备注；
   - 原子写入两个现金 effect；
   - 实际成交金额为事实，市场 FX quote 只用于分析，不能反向改写成交结果。
4. 交易结算使用投资标的报价币种，并从对应币种现金余额扣款或入账。
5. 账户详情按币种列出余额，同时显示换算后的家庭基础币种价值和使用的 FX 证据。

#### 验收标准

- 一个券商账户可同时持有至少 SGD、USD 等多个现金余额。
- 入金、出金、买卖、跨账户转账和账户内换汇都使用明确币种。
- 同账户换汇在一个事务中完成，不产生只有一侧成功的状态。
- 缺少市场汇率时不影响真实现金余额，只影响折算估值。

### 3.4 投资标的和汇率迁移到独立页面

**优先级：P1**

#### 问题

投资标的和汇率属于市场数据管理，不应隐藏在账户页的弹窗中。

#### 当前现状

- 账户页操作栏包含“投资标的”和“汇率”两个管理按钮。
- 投资标的以弹窗形式管理。
- FX 弹窗只列出当前投资组合估值所需要的币种对。
- 投资页面主要展示估值和收益，不负责完整的市场数据管理。

#### 解决方案

新增一级导航页面“市场数据”，包含两个页签或两个子页面：

1. **投资标的**
   - 标的资料；
   - 当前价格；
   - 报价来源、时间、新鲜度；
   - 手工价格和 provider 刷新；
   - 本地历史价格。
2. **汇率**
   - 已关注或估值所需币种对；
   - 当前汇率和明确方向；
   - 来源、时间、新鲜度；
   - 手工汇率和 provider 刷新；
   - 本地历史汇率。

账户页只保留与账户直接相关的持仓和现金入口。投资页继续负责组合估值、收益和配置分析。

#### 验收标准

- 投资标的和汇率有稳定的一级导航入口。
- 页面可在不联网的情况下展示本地当前值和历史数据。
- 账户页不再承担通用市场数据管理弹窗。
- 切换页面或刷新数据不会丢失未提交表单输入。

### 3.5 记忆并恢复窗口大小

**优先级：P1**

#### 问题

应用关闭时保存了窗口宽高，但重新启动时没有恢复。

#### 当前现状

- settings 包含 `WindowWidth` 和 `WindowHeight`。
- 关闭拦截器调用 `PersistWindowSize` 保存当前 Canvas 大小。
- 启动流程没有调用 `window.Resize` 使用已加载的宽高。

#### 解决方案

1. 加载并验证 settings 后、设置主内容前调用：

   ```go
   window.Resize(fyne.NewSize(preference.WindowWidth, preference.WindowHeight))
   ```

2. 为主窗口设置合理最小尺寸。
3. 保存时忽略最小化、零尺寸和超出范围的异常值。
4. 如果后续需要，可独立增加最大化状态和窗口位置；第一阶段只恢复宽高。

#### 验收标准

- 调整窗口大小、退出并重开后恢复到上次有效尺寸。
- 损坏或异常 settings 不会恢复出不可用窗口。
- 首次启动使用合理默认尺寸。

### 3.6 卡片文本换行与响应式布局

**优先级：P1**

#### 问题

一些长文本和操作栏会抬高控件最小宽度，导致卡片或整个内容区被横向撑大。

#### 当前现状

- `mutedLabel` 默认不换行。
- `keyValueRow` 的 label/value 不换行。
- badge 使用 `canvas.Text`，不支持自动换行。
- 账户行和多处操作栏使用 `HBox`。
- 账户筛选器使用固定五列网格。
- 投资收益使用固定四列网格。
- 历史筛选器使用包含多个控件的长 HBox。
- 左侧导航固定占用约 224px，进一步压缩主内容区。

仅给所有 Label 设置 `Wrapping` 不足以解决问题，因为 HBox、固定列网格和控件 MinSize 仍会决定页面最小宽度。

#### 解决方案

1. 提供统一的 wrapping label 组件，用于卡片正文、说明、错误、名称和长值。
2. 长值默认左对齐并允许多行；金额等短值可以保持右对齐。
3. 为操作区设计窄窗口布局：按钮换行、两列排列、垂直排列或收纳到更多菜单。
4. 五列筛选器按可用宽度切换为三列、两列或单列。
5. 四列表格在窄窗口切换为逐项卡片，不强制保持桌面表格布局。
6. badge 只用于短状态；长状态改用可换行 Label。
7. 增加 640px、800px、1100px 等典型窗口宽度的布局测试或截图测试。

#### 验收标准

- 长账户名、标的名、错误信息和多语言文案不会撑宽页面。
- 最小支持窗口宽度下不需要横向滚动才能操作主要功能。
- 窄窗口下按钮和筛选器仍可完整访问。

### 3.7 默认 FX Provider 使用 Frankfurter

**优先级：P1**

#### 问题

默认汇率查询应使用 Frankfurter，而不是 Yahoo Finance。

#### 当前现状

- `settings.DefaultFXProvider` 是 `yahoo_finance`。
- `Service.SetFXProvider("")` 会回退到 Yahoo Finance。
- 生产 registry 的注册顺序是 Yahoo Finance、Frankfurter，而 registry 又把第一个 provider 作为默认值。
- 投资标的价格仍需要 Yahoo Finance，这与 FX 默认使用 Frankfurter 不冲突。

#### 解决方案

1. 将 settings 默认 FX provider 改为 `frankfurter`。
2. 将空 FX provider 的 application fallback 改为 Frankfurter。
3. registry 使用显式 default key，不再依赖注册顺序。
4. Yahoo Finance 继续作为投资标的价格 provider。
5. 如果 settings 也采用破坏性更新，提升 settings schema，让新 generation 默认使用 Frankfurter。
6. 用户明确选择 Yahoo Finance 时仍应尊重该选择。

#### 验收标准

- 新安装或重置设置后，FX provider 为 Frankfurter。
- 投资标的刷新仍正常使用标的自身绑定的 Yahoo provider。
- provider 注册顺序变化不会改变默认 FX provider。
- 设置页可以在支持 FX 的 provider 之间切换并持久化。

### 3.8 数量为 0 的持仓和首次买入未持有标的

**优先级：P0/P1**

#### 问题

用户应能预先建立数量为 0 的持仓，也应能在买入时直接选择当前投资账户中尚未持有的标的。

#### 当前现状

- `Quantity` 允许非负数，因此数量 0 合法。
- domain、application 和 SQLite 都允许创建数量为 0 的持仓。
- 零持仓估值不要求价格或 FX，直接返回 0 且标记可用。
- 同一账户、同一标的只能有一个未归档持仓。
- 用户目前可以手工创建零持仓，再到历史页记录买入。
- 历史交易表单只列出已经存在的持仓。
- `TradeInput` 强制要求现存 `HoldingID`，因此不能直接买入尚未建仓的标的。

#### 解决方案

1. 继续允许用户手工创建零持仓，但在 UI 中将其标记为“零仓位”或“已关联标的”。
2. 零持仓不计入持仓数量、资产配置和主要持仓统计。
3. 买入表单改为先选择投资账户，再选择家庭下所有未归档投资标的。
4. application 增加类似 `RecordTradeForInstrument` 的用例：
   - 查找账户内已有活动持仓；
   - 没有时创建数量 0 的持仓；
   - 校验对应报价币种现金；
   - 原子写入持仓、买入 Activity、现金 effect、数量 effect 和成本信息。
5. 如果只有已归档旧持仓，默认创建新的持仓生命周期；如要恢复旧持仓，应要求用户明确选择。
6. 卖出仍只能选择实际存在且数量充足的活动持仓。

#### 验收标准

- 可以创建并查看数量为 0 的持仓。
- 可以在一次买入操作中选择账户尚未持有的标的。
- 自动建仓和买入在同一事务完成。
- 买入失败不会留下孤立零持仓。
- 零持仓不会扭曲 position count、资产配置或收益统计。

### 3.9 显示当前价格、当前汇率及本地历史数据

**优先级：P1**

#### 问题

投资标的应显示当前价格并允许查看历史价格；汇率也应显示当前值和历史数据。历史展示必须读取本地已保存事实，不应依赖打开页面时联网。

#### 当前现状

投资标的：

- `instrument_quotes` 保存手工和 provider 报价事实。
- repository 的 `ListInstrumentQuotes` 会按时间倒序读取全部本地历史。
- application 的 `CurrentInstrumentQuote` 会按标的当前 source preference 选择最新有效报价。
- 投资标的管理弹窗只显示名称、币种、类型和状态，不显示单价。
- 持仓详情显示的是数量乘价格后的总价值。
- 价格证据只显示来源、时间和新鲜度，不显示实际单价。
- 零持仓估值跳过报价选择，因此无法依赖持仓估值显示标的当前价格。

汇率：

- `fx_quotes` 保存手工和 provider 汇率事实。
- repository 的 `ListFXQuotes` 会读取家庭下全部本地汇率历史。
- 估值层按 FX preference 和方向选择最新报价。
- 当前 FX 弹窗不显示实际当前汇率，也不显示历史。

#### 解决方案

1. 在 application 层增加正式的只读 API：

   ```go
   InstrumentQuoteHistory(ctx, instrumentID, query)
   FXQuoteHistory(ctx, currencyA, currencyB, query)
   CurrentFXQuote(ctx, currencyA, currencyB)
   ```

2. `query` 至少支持时间范围、来源、分页/上限和排序方向。
3. 返回专用 view model，由 application 统一处理：
   - 当前 source preference；
   - 当前报价选择；
   - FX 正向/反向换算；
   - freshness；
   - 相同时间报价的稳定排序。
4. 市场数据页面显示：
   - 当前值；
   - 币种或汇率方向；
   - 报价时间；
   - 来源；
   - delayed/stale/manual 状态。
5. 历史展示同时提供折线图和明细表。表格是完整事实来源，图表是辅助展示。
6. 页面初次打开、筛选和切换标的只读取 SQLite。
7. 网络访问只由“刷新”按钮触发；刷新成功后重新读取本地数据。
8. 历史数据为空时明确显示“尚无本地报价”，不要显示 0。

#### 验收标准

- 每个投资标的都能独立显示当前单价，不依赖是否存在非零持仓。
- 每个已关注或估值所需币种对都能显示当前汇率和明确方向。
- 可以离线查看本地历史价格和历史汇率。
- 切换手工/provider source 后，当前值和历史筛选遵循一致规则。
- 缺少报价显示 unavailable，不以 0 代替。

### 数据库

- 空数据库创建最新 schema。
- 旧 schema 被只读识别并拒绝，不发生部分迁移。
- 当前 schema 完整性、外键、索引和约束验证。

- 同账户多币种余额。
- 同账户换汇的原子性。
- 买入未持有标的时自动建仓。

## 6. 实施时需要明确的产品决策

1. 旧数据库是自动切换到新文件、启动时要求用户重置，还是两者结合。
2. 旧 settings 是否全部废弃，还是只迁移无业务风险的外观设置。
3. 零持仓是否出现在投资主页面，还是只出现在账户详情的“零仓位”区域。
4. 买入遇到已归档旧持仓时，是创建新持仓还是允许恢复旧持仓。
5. 市场数据历史首版只提供表格，还是同时提供折线图。
6. 历史行情默认展示所有来源，还是只展示当前 source preference。
7. 是否允许用户关注当前投资组合暂时不需要的 FX 币种对。

这些产品决策不影响本文对当前代码缺口的判断，但会改变具体 UI 和数据生命周期设计。
