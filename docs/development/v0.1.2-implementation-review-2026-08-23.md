# v0.1.2 Implementation Review — 2026-08-23

## Review conclusion

The v0.1.2 implementation is structurally coherent: domain, application,
SQLite, provider adapters, and Fyne remain separated; financial decimals do
not cross the boundary as binary floats; provider requests are explicit; and
the existing automated gates pass. The review nevertheless found **10 open
issues**: **2 High**, **7 Medium**, and **1 Low**.

The highest-risk items are:

1. a provider-supplied future timestamp can become the permanently selected
   quote, and an extreme timestamp can make later SQLite reads fail; and
2. schema migration commits before the new schema is verified, so a failed
   post-migration verification can leave the primary database modified.

This document is findings-only. No implementation code was changed as part of
this review.

- **High** — can corrupt or strand persisted data, or break a locked release

  creates a material reliability/performance risk.
- **Low** — release evidence or defensive coverage is incomplete without a
  presently demonstrated production failure.

## Detailed findings

### V012-01 — Provider timestamps are not bounded

**Severity:** High

**Evidence**

- `internal/infrastructure/marketdata/yahoo.go:311-315` and `:340-344`
  accept Yahoo timestamps through `unixTimestamp`.
- `internal/infrastructure/marketdata/yahoo.go:385-389` rejects only values less
  than or equal to zero. It accepts arbitrarily distant future Unix values.
- `internal/application/refresh.go:177-184` validates only that the time is
  non-zero before persisting it.
- `internal/domain/valuation.go:18-32` treats a negative age (quote time later
  than `now`) as `Fresh`.
- `internal/infrastructure/sqlite/repository.go:880-881` formats the time into
  text, while `internal/infrastructure/sqlite/portfolio_repository.go:872-877`
  later requires that text to parse as RFC 3339.

**Failure chain**

1. Yahoo returns a positive but future `regularMarketTime`, or the same value
   appears in a fallback timestamp array.
2. The adapter accepts and persists it.
3. Deterministic latest-quote selection prefers that future observation over
   all normal later refreshes.
4. A plausible future timestamp remains `Fresh` indefinitely. An extreme year
   that cannot round-trip through RFC 3339 causes subsequent portfolio snapshot
   reads to return an integrity error.

This crosses the release's locked boundary that provider data is untrusted and
must be safely normalized before persistence.

**Recommended correction**

- Validate provider observation time before domain construction and before
  persistence: require a sensible lower bound, an upper bound such as
  `now + clockSkewTolerance`, and successful round-trip through the persistence
  timestamp format.
- Apply the same policy to both Yahoo timestamp paths and to other providers'
  externally supplied dates/times.
- Treat any future timestamp beyond tolerance as a malformed provider response;
  do not write it and keep the last valid local quote.

**Required regression tests**

- regular-price and fallback fixtures with a timestamp beyond the allowed
  future tolerance;
- the largest positive Unix timestamp;
- proof that the invalid response writes no quote;
- database reopen/read after every accepted boundary timestamp; and
- `QuoteFreshness` coverage for small tolerated skew and rejected future time.

### V012-02 — Migration commits before the new schema is verified

**Severity:** High

**Evidence**

- `internal/infrastructure/sqlite/database.go:102-163` runs migrations, sets
  `user_version`, and commits the transaction.
- `internal/infrastructure/sqlite/database.go:170-176` calls `DB.Verify` only
  after the commit. On failure it closes the database and returns
  `StatusIntegrityFailed`; it does not restore the primary file.
- `internal/infrastructure/sqlite/schema3.sql:1-97` uses `IF NOT EXISTS` for all
  new tables and indexes. A colliding, incompatible pre-existing object can be
  silently reused during migration and discovered only after commit.
- The release plan requires a failed migration to block startup and preserve
  the original database (`v0.1.2-implementation-plan.md:108-113`).

**Impact**

A schema-2 file containing an unexpected same-named schema object can have its
`user_version` advanced to 3 and other schema objects committed, then fail
verification. A recoverable sibling snapshot exists, but the primary database
that the application will try to open next has already changed. Recovery is
not automatic or exposed as an in-app workflow.

**Recommended correction**

- Verify the complete target schema through the same migration transaction
  before commit. Helpers used by `Verify` should accept a transaction/query
  interface.
- Prefer migrations that fail on an unexpected name collision rather than
  masking it with `IF NOT EXISTS`.
- If any required verification cannot run transactionally, restore the primary
  database from the pre-migration snapshot before returning the bootstrap
  error, and verify the restored file.

**Required regression tests**

- A schema-2 fixture with a same-named but incompatible table.
- A schema-2 fixture with a same-named but incompatible index.
- For each failure, compare the original database bytes or a complete schema and
  business-data fingerprint, and assert that `user_version` remains 2.
- Reopen the failed database to prove no partial migration remains.

### V012-03 — A 429 from one provider skips another provider's targets

**Severity:** Medium

**Evidence**

- `internal/application/refresh.go:127-142` tracks one operation-wide
  `rateLimited` boolean and skips every subsequent target after the first 429.
- `internal/application/refresh.go:156-159` resolves FX targets through the
  selected FX provider but Instrument targets through each Instrument's saved
  provider.
- `internal/application/refresh.go:282-287` sorts by target key, so `fx:`
  targets run before `instrument:` targets.

**Impact**

With Frankfurter selected for FX, a Frankfurter 429 causes all later Yahoo
Instrument targets in `RefreshAll` to be marked skipped even though Yahoo was
never called and may be healthy. The release contract's operation-local 429
stop is intended to protect a rate-limited provider, not to couple independent
providers.

**Recommended correction**

Track rate limiting by resolved provider key. Stop only later targets owned by
the provider that returned 429, and continue targets routed to other providers.
Keep result ordering deterministic.

**Required regression tests**

- Frankfurter FX returns 429, followed by a successful Yahoo Instrument target.
- Yahoo returns 429 while another registered FX provider remains callable.
- Multiple targets for the same rate-limited provider are skipped without
  further network calls.

### V012-04 — Investments exposes raw Instrument UUIDs

**Severity:** Medium

**Evidence**

- `internal/ui/investments_page.go:89-99` labels an Instrument component with
  `component.InstrumentID.String()`.
- `internal/ui/investments_page.go:79-83` passes `nil` Instrument metadata into
  missing-input formatting, which also falls back to the ID.
- Existing `internal/ui/investments_page_test.go` coverage checks construction
  and controls but not the household-facing text of a position or missing-price
  row.

**Impact**

The main Investments page presents internal UUIDs where a family user needs an
Instrument name and, when available, a familiar symbol. The position and
missing-price sections therefore fail the release story that quote evidence and
missing inputs are understandable.

**Recommended correction**

Add a presentation-safe Instrument identity (name, optional symbol) to the
authoritative valuation/read model, or provide the page with the same snapshot's
Instrument map. Avoid a per-row repository lookup. Use a stable label such as
`Name (SYMBOL)` with `Name` as the fallback.

**Required regression tests**

- Position rows display name/symbol and never the UUID.
- Missing-price rows display the same identity.
- Archived retained references and missing metadata have a localized, readable
  fallback.

### V012-05 — Optional Instrument fields cannot be cleared

**Severity:** Medium

**Evidence**

- `internal/ui/portfolio_pages.go:501-516` submits the complete edit form,
  including empty text values.
- `internal/application/portfolio.go:14-28` has no `...Set` flags or another
  tri-state representation for optional Instrument fields.
- `internal/application/portfolio.go:456-495` interprets empty string, `nil`,
  and zero as "keep the current value" for Symbol, market/country metadata,
  ISIN, Note, logo, provider metadata, and sort order.

**Impact**

After a user stores a symbol, market code, country code, ISIN, note, or similar
optional value, deleting it in the edit dialog and saving silently restores the
old value. `SortOrder` also cannot intentionally be changed to zero. This is a
data-maintenance failure in a core v0.1.2 workflow.

**Recommended correction**

Make update semantics explicit. Either use full replacement for the complete
UI form, or add per-field `Set` flags/pointer wrappers like
`HoldingUpdateInput`. Keep omitted/preserve distinct from explicitly empty/clear.
Define separately whether changing source to Manual must clear or retain the
provider binding.

**Required regression tests**

- Clear every optional text field and Note from a populated Instrument.
- Change sort order from non-zero to zero.
- Switch Provider to Manual and verify the chosen binding-retention policy.
- A partial programmatic update still preserves fields only when they were
  genuinely omitted.

### V012-06 — Unsaved FX Provider selection can report a no-op as success

**Severity:** Medium

**Evidence**

- `internal/ui/portfolio_pages.go:673-679` enables Refresh as soon as the local
  source selector changes to Provider.
- The preference is persisted only by Save at
  `internal/ui/portfolio_pages.go:680-692`.
- `internal/application/refresh.go:274-280` derives refresh eligibility from the
  persisted preference; an unsaved Manual/missing preference produces
  `RefreshSkipped`.
- `internal/ui/refresh_worker.go:165-171` treats only Failed and RateLimited as
  needing attention. `internal/ui/portfolio_pages.go:652-668` therefore closes
  the dialog for the skipped result.

**User-visible sequence**

1. Open a required FX pair currently set to Manual or without a preference.
2. Select Provider.
3. Press Refresh without first pressing Save.
4. No preference is saved and no provider request occurs, but the dialog closes
   as though the operation succeeded.

**Recommended correction**

Choose one explicit flow:

- persist the Provider preference successfully before starting Refresh; or
- keep Refresh disabled until Save succeeds.

In either flow, a skipped single-target refresh must remain visible and must not
close the dialog as success.

**Required regression tests**

- The exact Manual -> Provider -> Refresh sequence.
- Persist failure preserves the open dialog and selection.
- Skipped/not-found/unavailable single-target results remain visible and offer
  a useful next action.

### V012-07 — `DB.Verify` validates names, not schema definitions

**Severity:** Medium

**Evidence**

- `internal/infrastructure/sqlite/database.go:213-255` records only whether
  required column names exist. It ignores type, nullability, defaults, primary
  keys, checks, and foreign-key definitions.
- `internal/infrastructure/sqlite/database.go:256-290` records only whether
  required index names exist. It ignores indexed columns and order, uniqueness,
  and partial-index predicates.
- The technical design requires table/column/index fingerprints
  (`v0.1.2-technical-design.md:322-326`).

**Impact**

A database can pass `Verify` with, for example, a non-unique or wrongly keyed
index named `ux_holdings_active_account_instrument`. The application then runs
without the uniqueness or query-ordering properties that the repository assumes.
This also weakens V012-02 because `IF NOT EXISTS` trusts colliding names.

**Recommended correction**

Fingerprint schema semantics using `PRAGMA table_info`, `index_list`,
`index_xinfo`/`index_info`, `foreign_key_list`, and the normalized partial-index
SQL from `sqlite_master`. Check at least type/nullability/PK, index column order,
unique/partial flags and predicate, and required foreign-key delete behavior.

**Required regression tests**

For every required schema object class, mutate one property while retaining the
same object name and prove `Verify` returns `StatusIntegrityFailed`.

### V012-08 — Valuation snapshots load all append-only history

**Severity:** Medium

**Evidence**

- `internal/infrastructure/sqlite/portfolio_repository.go:17-83` builds every
  Overview/Account/Portfolio snapshot in one read transaction.
- `internal/infrastructure/sqlite/portfolio_repository.go:533-557` selects all
  cash observations, all Instrument quotes, and all FX quotes for the Household.
- Valuation later chooses the latest observations in Go, so older rows are read,
  parsed, allocated, and retained even though they cannot affect current value.
- The implementation plan requires query-count tests for bounded snapshot
  loading (`v0.1.2-implementation-plan.md:97-117`), but there is no test that
  instruments the query count or bounds returned history volume.

**Impact**

Every explicit refresh appends history. Consequently ordinary navigation and
valuation become O(total historical observations), while holding a read
transaction on the single SQLite connection. The cost grows for the lifetime
of the Household and can eventually stall the Fyne UI and delay writes.

**Recommended correction**

Keep history-list APIs separate. For the current valuation snapshot, select
only the latest relevant candidate per account/currency, Instrument/source, and
normalized FX pair/source using a window function or a deterministic correlated
subquery matching the locked quoted/effective time, created time, ID ordering.
Preserve one consistent transaction and a fixed query count.

**Required regression tests**

- Instrument SQL calls and assert a fixed query count independent of entity
  count.
- Seed large histories and assert the snapshot returns only bounded candidates.
- Prove latest selection and ties remain identical to current semantics.
- Add a bulk-history benchmark for current snapshot/valuation latency.

### V012-09 — Zero-quantity Holdings require price and FX inputs

**Severity:** Medium

**Evidence**

- Quantity explicitly permits zero (`internal/domain/decimal.go:20-48`), and the
  release contract promises non-negative quantities.
- `internal/application/valuation.go:266-277` selects a quote before multiplying
  by quantity. With no quote, it emits `MissingInstrumentPrice` even when the
  quantity is exactly zero.
- If a price exists but the Instrument is foreign-currency, the same zero value
  can also require an FX preference/quote in `internal/application/valuation.go:284-315`.

**Impact**

A closed-out position retained at quantity zero can make its Account, Overview,
and Investments aggregates incomplete even though its exact native and base
contribution is known to be zero. The UI asks a family user to maintain
irrelevant market inputs for an empty position.

**Recommended correction**

Short-circuit active zero-quantity Holdings to an available zero component
without requiring price or FX. Alternatively, explicitly exclude zero positions
from current valuation and document that presentation rule. In neither case
should zero create a missing input.

**Required regression tests**

- Zero quantity with no price, no FX preference, and no FX quote.
- Zero quantity with stale historical quotes.
- Mixed zero and non-zero Holdings preserve correct completeness and subtotal.

### V012-10 — Archive invariants can race with Holding/cash writes

**Severity:** Low

**Evidence**

- `internal/application/portfolio.go:211-244` checks that a Holding is active in
  a snapshot, then performs a separate repository update.
- `internal/infrastructure/sqlite/portfolio_repository.go:193-199` updates by
  Holding ID only, without rechecking `archived_at` or Household inside the
  write.
- `internal/application/portfolio.go:258-290` similarly checks that an Account
  is active before appending cash.
- `internal/infrastructure/sqlite/portfolio_repository.go:245-259` rechecks
  TrackingMode but not `archived_at` in the write transaction.

**Impact**

If an archive operation commits after the application snapshot but before the
write, an archived Holding can still be edited or a cash observation can be
appended to an archived Account. The UI normally reduces the window, but the
application service and background goroutines do allow concurrent calls, so the
repository should own the final invariant.

**Recommended correction**

Move the active-target and Household checks into each write transaction. Use a
conditional update/join or select-and-write in one `DB.WithTx`, and map zero
affected rows to a stable validation/conflict error.

**Required regression tests**

- Deterministically interleave archive between application read and write for
  Holding update and cash append.
- Assert the later mutation writes nothing and returns the stable safe error.
- Run these tests with `-race`.

## Known release-closeout gaps (not new review findings)

The active release documents already state that Phase 10 is incomplete. These
items should remain release blockers, but they are not counted in the ten

- isolated desktop launch against a disposable database;

- packaging/signing/notarization verification on the release artifact; and
- current provider smoke evidence, kept separate from deterministic default

## Verification performed

The following checks passed against the reviewed tree:

```text
go test ./...
go vet ./...
go test -race ./internal/application ./internal/infrastructure/marketdata ./internal/infrastructure/sqlite ./internal/ui
go build ./cmd/nestworth
gofmt -l cmd internal
```

`gofmt -l` produced no file names. The macOS linker emitted its existing
duplicate `-lobjc` warning. After the successful build, Go also warned that it
could not write a module stat-cache temporary file outside the workspace; that
warning did not change the successful build exit status.

The passing gates do not invalidate the findings: each finding is on a branch,
state transition, malformed external input, concurrency interleaving, or
long-lived data-volume condition not exercised by the current suite.

## Suggested fix order

1. V012-01 and V012-02, then V012-07: close persistence and migration integrity
   risks first.
2. V012-06, V012-04, and V012-05: repair the family-facing edit/refresh/read
   workflows.
3. V012-03 and V012-09: correct refresh and valuation semantics.
4. V012-08: bound current reads before quote history grows.
5. V012-10: move the last archive invariants into repository transactions.
6. Re-run Phase 10 only after the relevant automated regressions are in place.
