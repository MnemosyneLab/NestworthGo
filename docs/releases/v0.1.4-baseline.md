# v0.1.4 Compatibility Baseline

## Purpose and Status

**Status:** `Historical Phase 0 baseline; superseded by the shipped schema-6
generation on 2026-08-24`.

The current v0.1.4 database is created directly from
`internal/infrastructure/sqlite/schema.sql`; use
`testdata/v0.1.4/schema6-fixture.sql` for current fixture evidence. This
document preserves the pre-implementation baseline facts and is not a
database-migration contract.

This document records what the v0.1.4 design may rely on and what Phase 0 must
verify before implementation. It deliberately separates released Go behavior,
approved v0.1.3 contracts, and uncommitted work in progress.

The archived Rust/Tauri v0.1.4 documents
(`../legacy/rust-tauri-inherited-unreviewed/releases/v0.1.4*.md`) are historical
input only. Their FIFO lot ledger, unknown-basis declaration workflow, TWR/XIRR
return engine, schema numbers, IPC commands, and release evidence are not
compatible with this repository and are not the design this document freezes.

## Product Precondition: No Public Release Exists

Nestworth-go has not published a public release. No real user database exists
outside development and test fixtures. This changes what v0.1.4 must protect
compared to v0.1.2 and v0.1.3:

- v0.1.4 does **not** need an unknown-basis declaration/revocation workflow for
  pre-existing Holdings, because there is no shipped version whose users could
  already hold a position with no recorded cost.
- v0.1.4 **may** require a new mandatory field (cost + acquisition date) at the
  exact moments a Holding's quantity first enters recorded history, without
  designing a backward-compatible "unknown basis" state for it.
- The schema `5 -> 6` migration may include an application-owned backfill step
  (not only pure SQL) that assigns a default cost basis to any Holding that
  already has positive quantity in a development/test database at migration
  time. This is acceptable because no real financial history is being
  reinterpreted for an actual user; it is a fixture repair, not a release-grade
  data migration guarantee.

This precondition does not relax any other v0.1.1/v0.1.2/v0.1.3 invariant.
Every other promise below is preserved exactly as in the v0.1.3 baseline.

## Approved v0.1.3 Dependency

v0.1.4 assumes the completed v0.1.3 release provides:

- one immutable `HistoryOrigin` per Household with typed
  `HistoryOriginComponent` rows of kind `account_value`, `account_cash`, or
  `holding_quantity` (`internal/infrastructure/sqlite/schema4.sql:19-39`);
- immutable `Activity` records with ordered `ActivityEffect` rows targeting
  `account_value`, `account_cash`, or `holding_quantity`
  (`internal/infrastructure/sqlite/schema4.sql:82-124`);
- `activity_trade_details` carrying `side`, `instrument_id`, `holding_id`,
  `quantity`, `gross_amount`/`gross_currency`, a derived `unit_price`, and an
  optional `fee_amount`/`fee_currency` for every Buy/Sell
  (`internal/infrastructure/sqlite/schema4.sql:126-140`);
- `Holding.Quantity` as the current projection, with `holding_quantity_values`
  as its append-only observation history
  (`internal/domain/portfolio.go:174-224`,
  `internal/infrastructure/sqlite/schema4.sql:152-163`);
- Undo/Fix via `ActivityReversal` and `ActivityCorrectionGroup`, where a
  reversed Activity and its reversal both remain persisted evidence
  (`internal/domain/change.go:587-612`);
- `PositionAdjustmentInput`, the typed command used by the post-History
  Holding-creation workflow to reconcile a new Holding's starting quantity
  without a trade (`internal/domain/change.go:386-397, 904-935`);
- `DailyValuationSnapshotItem` at Account/Holding/Instrument granularity with
  quote/FX evidence and an explicit `Complete`/`MissingReason`
  (`internal/domain/history.go:190-206`);
- one authoritative `ValuationService.PortfolioSnapshot`/`ValueAccounts` path
  used by both current and historical (cutoff-parameterized) valuation
  (`internal/application/valuation.go:16-153`);
- exact decimal `Money`, `Quantity`, `UnitPrice`, and `FxRate` types with fixed
  precision and canonical string parsing (`internal/domain/decimal.go`).

No v0.1.4 schema migration may be written until these facts are verified
against the actual completed v0.1.3 code at the frozen commit. If any shape
differs, Phase 0 updates the v0.1.4 design and migration number before
implementation.

## Phase 0 Freeze Package

Phase 0 has committed and verified a sanitized schema-5 fixture and a machine-readable summary
covering:

- exact schema version (`5`), table/column/index/foreign-key fingerprint, and
  the full migration path from schema 1;
- the exact shape of `Holding`, `Activity`, `ActivityEffect`, `TradeDetail`,
  `HistoryOriginComponent`, and `PositionAdjustmentInput` used for cost-basis
  design;
- deterministic quote/FX selection rules already implemented in
  `ValuationService` (`selectInstrumentQuote`, `selectFXQuote`,
  `findFXPreference`) that v0.1.4 must reuse rather than reimplement;
- Fyne page/controller ownership for Investments (`investments_page.go`),
  History (`history_page.go`), and Analytics (`analytics_page.go`, currently a
  net-worth trend placeholder);
- normal test, vet, race, formatting, and release gates at the frozen commit.

Phase 0 evidence is current Go/Fyne evidence: the fixture opens at schema 5,
passes SQLite integrity and foreign-key checks, includes Starting Point,
Buy/Sell, Position Transfer, Undo, and Fix evidence, and is accepted by the
current repository verifier without migration or network access. The schema
`5 -> 6` backfill is an explicitly open development-fixture repair item; it
must not be treated as a release-grade rewrite of a future real user database.

The fixture must contain:

- a confirmed Household timezone, base currency, and at least one Member;
- a Holdings Account with a Starting-point-captured Instrument position and at
  least one post-history Buy and one Sell of the same Instrument;
- a Position Transfer between two Holdings Accounts for the same Instrument;
- an Undo and a Fix entry affecting at least one Buy;
- manual and Provider Instrument/FX quotes spanning the fixture's date range;
- no personal data, credential, production path, provider token, or real
  portfolio identifier.

## v0.1.4 Golden Compatibility Cases

Before feature work, freeze expected outcomes for:

| Case | Required invariant |
| --- | --- |
| Fresh migration to schema 6 | Every v0.1.1/v0.1.2/v0.1.3 identity, observation, and current total is unchanged |
| Starting Point with an existing Instrument position | Capturing the Starting point requires and stores a per-unit cost and date for that Holding; zero Activities are fabricated |
| First Buy for a new Holding | Cost basis equals the Buy's derived unit price; no separate cost entry is required |
| "Already existed" reconciliation (`PositionAdjustmentInput`, `Added=true`) | Requires an explicit per-unit cost; the Fyne form defaults it to the current quote and today, and the user may override |
| Second Buy of the same Holding | Average cost becomes the quantity-weighted blend of the prior average and the new Buy |
| Sell | Realized gain uses the average cost in effect immediately before that Sell; average cost for the remaining quantity is unchanged |
| Position Transfer | The destination Holding's average cost blends in the source's average cost as of the transfer; the source Holding's average cost for its remaining quantity is unchanged |
| Undo of a Buy | Average cost and realized gain recompute as if the undone Buy never existed |
| Missing current quote | Cost basis remains visible; unrealized gain is reported unavailable, never zero |

Each golden must assert persisted facts and application output, not a UI
screenshot. The remaining v0.1.4 goldens are input contracts for later phases
and are not claimed as implemented before their phase lands.

## Preserved Contracts

v0.1.4 must preserve every v0.1.1, v0.1.2, and v0.1.3 promise, including:

- every identity, relationship, Ownership share, archive state, value, and
  Activity/history fact already recorded;
- deterministic current observation and quote/FX selection after v0.1.4 loads;
- no network during startup, normal reads, Record change, Undo/Fix, historical
  valuation, snapshot rebuild, migration, or the new gain calculation;
- future-schema refusal without business-data or settings writes.

## Intentional v0.1.4 Changes

- Every path that gives a Holding positive quantity for the first time inside
  recorded history (Starting Point capture, `PositionAdjustmentInput` with
  `Added=true`, or the first Buy) must be able to resolve a per-unit cost and
  an acquisition date for that quantity.
- Average cost and realized/unrealized gain are read models derived by
  replaying a Holding's non-reversed Activities and its Starting Point cost,
  not new mutable projection columns. See the
  [technical design](v0.1.4-technical-design.md) for the replay contract.
- `HistoryOriginComponent` of kind `holding_quantity` gains a required
  `unit_cost` value when quantity is positive.
- These changes may add data and stronger validation. They may not reinterpret
  an existing Activity, effect, or Starting Point component as a different
  kind of change than it already is.

## Release Evidence That Cannot Be Inherited

Rust unit counts, Tauri command/binding checks, React routes, the legacy
`004_analytics` migration, lot-ledger test names, XIRR/TWR goldens, and any
signing/notarization record from the archived Rust/Tauri v0.1.4 documents do
not prove any Go/Fyne v0.1.4 behavior. The Go release must generate fresh
evidence through its own implementation plan.
