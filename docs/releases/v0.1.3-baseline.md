# v0.1.3 Compatibility Baseline

## Purpose and Status

**Status:** `Design baseline; implementation evidence not yet frozen`.

This document records what the v0.1.3 design may rely on and what Phase 0 must
verify before implementation. It deliberately separates released Go behavior,
approved v0.1.2 contracts, and uncommitted work in progress.

The archived Rust/Tauri v0.1.3 baseline is historical input only. Its schema,
commands, service names, phase status, and release evidence are not compatible
with this repository.

## Verified Repository Baseline

At design freeze, commit `234dc0c` provides the implemented v0.1.1 baseline
plus v0.1.2 Phases 0-2:

- Go + Fyne desktop application with `application.Service` as the UI facade;
- SQLite schema `3` with ordered schema-2 migration and verification;
- one Household, Members, Institutions, Groups, Accounts, Ownership, append-only
  Account Values, archive/restore, media, settings, and backend-owned Overview;
- exact decimal Money, Quantity, UnitPrice, and FxRate plus typed portfolio IDs;
- Instrument, Holding, cash, quote, FX preference domain contracts and schema-3
  repositories, including a bounded portfolio snapshot read;
- transaction ownership in the SQLite repository/DB layer;
- Activity navigation present only as a placeholder.

This does not make v0.1.2 complete. Manual portfolio use cases, authoritative
valuation integration, Fyne workflows, provider refresh, and release closeout
remain later phases at this baseline.

## Approved v0.1.2 Dependency

v0.1.3 assumes the completed v0.1.2 release will provide:

- schema `3` Instruments, Holdings, Holdings Account cash, Instrument Quotes,
  FX Quotes, and FX Preferences;
- Quantity, UnitPrice, FxRate, and Money as canonical decimal strings;
- append-only current Account Value, cash, price, and FX observations;
- one bounded portfolio snapshot read and one authoritative ValuationService;
- explicit Manual/Provider selection with no silent fallback;
- current-day valuation with exact provenance and partial-valued subtotals;
- Yahoo only behind an explicit current refresh action; ordinary reads and all
  manual workflows remain offline.

No v0.1.3 schema migration may be written until these facts are verified in the
completed v0.1.2 code. If its schema version or shape differs, Phase 0 updates
the v0.1.3 design and migration number before implementation.

## Phase 0 Freeze Package

Phase 0 must commit a sanitized schema-3 fixture and a machine-readable summary
covering:

- exact schema version, table/column/index/foreign-key fingerprint, and migration
  path from schema 2;
- application and repository interfaces used for Accounts, Holdings, values,
  cash, quotes, preferences, archive state, and portfolio snapshot reads;
- deterministic latest-observation ordering and selected-source rules;
- Fyne page/controller ownership and the actual replacement point for the
  Activity placeholder;
- normal test, vet, race, formatting, package, accessibility, and release gates;
- zero-write/no-network behavior when a future schema is opened.

The fixture must contain:

- Household timezone input, base currency, Members, Ownership, and retained
  archived references;
- Balance, Manual Value, and Holdings Accounts in more than one currency;
- active and zero-Quantity Holdings, multi-currency cash, Manual and Provider
  quote observations, and explicit source preferences;
- the v0.1.2 complete `62190 CNY` golden and partial `40990 CNY` golden;
- no personal data, credential, production path, provider token, or real
  portfolio identifier.

## v0.1.3 Golden Compatibility Cases

Before feature work, freeze expected current and historical outcomes for:

| Case | Required invariant |
| --- | --- |
| Start from existing state | Starting point equals the selected v0.1.2 state; zero Activities are fabricated |
| Same-currency transfer | Source plus destination net to zero Household inflow/outflow |
| Cross-currency transfer | Both native amounts survive; rate is destination divided by source |
| Buy with fee | Quantity and gross principal are internal; explicit fee alone reduces net worth |
| Value update | New absolute value produces one derived difference; unchanged value writes nothing |
| Fix entry | Original remains resolvable; inverse and replacement commit together |
| Missing historical quote | Valued subtotal remains visible and complete is false; missing component is not zero |
| Today-only change | Current view updates; no closed-day history work remains pending |

Each golden must assert persisted facts and application output. UI screenshots
alone are not compatibility evidence.

## Preserved Contracts

v0.1.3 must preserve:

- every v0.1.1 identity, relationship, Ownership share, archive state, value,
  media reference, and settings fact;
- every completed v0.1.2 Instrument, Holding, cash, quote, and preference fact;
- existing current-value results before History is explicitly started;
- deterministic current observation selection after History starts;
- no network during startup, normal reads, Record change, Undo/Fix, historical
  valuation, snapshot rebuild, migration, or database verification;
- future-schema refusal without business-data or settings writes.

## Intentional v0.1.3 Changes

- Financial amount and Quantity mutations route through Record change after the
  Starting point exists.
- Current observation tables gain traceable projection metadata; pre-v0.1.3
  rows remain valid legacy observations.
- History adds immutable event facts, effective state/preference observations,
  and replaceable daily valuation cache revisions.
- The former Activity placeholder becomes the family-facing History page.

These changes may add data and stronger validation. They may not reinterpret an
old observation as income, spending, a trade, or a transfer.

## Release Evidence That Cannot Be Inherited

Rust unit counts, Tauri command/binding checks, React routes, old migration
numbers, performance measurements, screenshots, signing, and notarization do
not prove any Go/Fyne v0.1.3 behavior. The Go release must generate fresh
evidence through the implementation plan.
