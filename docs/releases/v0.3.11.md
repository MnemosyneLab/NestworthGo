Application versions have advanced by PATCH through v0.3.10, with one increasing
build number per release. This preparation continues that sequence at v0.3.11 /
build 12. The MCP breaking contract and skill keep their independent versions.
No financial-schema bump is needed. See the [prepared notes](v0.3.11-notes.md)
and [unreleased changelog](../../CHANGELOG.md) for changes since v0.3.10.

Metadata is synchronized in `internal/version`, frontend package metadata,
Wails configuration, Darwin production/development plists and packaging defaults,
Linux linker/nFPM metadata, and Windows version resources/manifests/installers.
Linux and Windows metadata consistency does not establish supported native
packages for those platforms.

## Remaining release checks

| Gate | Required evidence before publication |
| --- | --- |
| Selected source | Choose the reviewed merged SHA; tie every final artifact and check to that exact unchanged source. |
| Automated checks | Record exact-source native Mac `check` results, provider-module acceptance and relevant scheduled/manual perf/race results, including any failures. PR validation is recorded in its description and Actions runs. |
| Native package | Run `wails3 task package:release` on Apple Silicon macOS with the pinned toolchain. Verify identity/build/arm64/minimum OS, microphone declaration, resources, strict signatures, complete DMG/ZIP payload equality and checksums. |
| Skill | Run the static/version guard and installer/tooling tests, package skill 3.0.21, verify its checksum and source contents without modifying installed user skills. |
| Archive acceptance | Launch/relaunch each actual DMG/ZIP payload using separate synthetic database/settings paths; verify onboarding, persistence and normal Quit. Follow the [packaging procedure](../development/local-workflow.md#release-artifacts-and-isolated-mac-acceptance). |
| GUI and integrations | Record affected native desktop/mobile/review/AI flows, microphone permissions, accessibility, compatible external MCP client and real-provider results separately from unit, browser and fake-provider tests. |
| Signing / notarization | Existing tasks use ad-hoc signing. Developer ID, notarization and Gatekeeper acceptance require separate evidence or an explicit release-specific owner decision. |
| Publication | After separate authorization, retain source identity, final hashes and acceptance record; verify tag target and uploaded/downloaded artifact bytes. |

These gates are pending for the final release candidate. Passing earlier PRs or
v0.3.10's publication waivers does not turn them into passed v0.3.11 acceptance.
This preparation creates no tag, release or official uploaded artifacts.
