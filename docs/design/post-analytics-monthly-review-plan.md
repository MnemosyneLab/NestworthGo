## 1. 这轮要解决什么

Analytics 回答“发生了什么”，下一轮帮助用户完成一次可信的日常维护：

> 我核对了这个月的重要资产，知道哪些数字还不可靠，也知道补录历史后哪些结论需要重新看。

目标是形成一个每月愿意重复使用的流程：

**检查数据 → 对照外部记录 → 处理差异 → 理解本月变化 → 保存核对记录 → 确认备份情况。**

对主要只有一个用户的本地应用，优先减少维护时间和解释成本。第一版不设强制月末任务，不要求每天记账，不把应用变成预算或会计结账系统。用户也可以在月中对最近一个已闭日进行核对。

完成这轮以后，理想使用场景是：打开一个入口就知道该看哪些账户、哪些价格或历史有缺口；已确认的内容能记住；以后相关输入变化时，不会继续把旧核对状态当成有效结论。

## 2. 基础能力与新增范围

以下是编写方案时核对的复用点；Analytics 全部完成后，应再确认最终 DTO 和导航入口。

| 能力 | 当前依据 | 下一轮怎么用 |
|---|---|---|
| 资产变化、收益及 completeness | Analytics application/Wails projections、设计与开发计划 | 复用最终分析 API，不新增第二套财务算法 |
| History Origin、历史快照、dirty/completed cursor | [history API](../../internal/wailsapi/history/history.go)、[historical_snapshot.go](../../internal/application/historical_snapshot.go) | 确定可核对期间、已闭日和重算状态 |
| 补录、更正、reconciliation、数量调整 | [change.go](../../internal/domain/change.go)、History Preview/Record/Fix 入口 | 差异处理仍经过现有预览和确认写入路径 |
| 备份、校验、恢复、最近备份摘要 | [备份恢复设计](backup-restore-and-csv-portability.md)、[backup_port.go](../../internal/application/backup_port.go) | 展示现有证据并提供入口，不重建恢复系统 |
| Accounts/Holdings CSV | 现有 create-only 预览、确认、提交契约 | 保持现有语义；银行流水匹配属于后续独立计划 |

这轮新增的核心能力只有四项：

1. 将数据问题集中呈现，并提供具体处理入口。
2. 按同一截止日期核对现金余额、持仓数量和手工估值。
3. 保存核对范围、结果和未解决事项。
4. 相关历史变化后，明确提示旧核对依据已改变。

“没有缺失行情”“用户核对过余额”“备份创建时已校验”是三种不同证据。页面应分别展示，不能压缩成一个笼统的绿色“数据全部正确”。

## 3. 用户流程与信息呈现

### 3.1 入口与默认期间

第一版建议从 Overview 的“核对资产”入口进入专用页面，暂不增加长期占用侧栏的一级分类。页面支持中途离开和返回，处理问题不要求用户一直留在向导里。

- 默认选择最近一个完整自然月；没有该月历史时，使用可覆盖期间并明确提示。
- 支持修改期间，截止日不得晚于 History Origin 时区的 last closed day。
- 期间起点不能早于 History Origin；开始记录的第一个月明确标记“部分月份”。
- 月份/日期是家庭历史时区的本地日期，不能按浏览器时区或固定 24 小时推导日界线。
- 当期间完全无历史覆盖时展示说明，不生成零余额或空的“核对成功”。

页面展示三个独立区域：

| 区域 | 主要内容 |
|---|---|
| 数据准备 | 历史覆盖、快照状态、报价/汇率缺失、估值待更新、未解释差额 |
| 账户核对 | 各账户的截止日余额/持仓、已核对状态、差异及处理入口 |
| 本期结论 | 资产变化与收益入口、保留问题、保存记录、最近备份情况 |

打开页面只读取本地数据，不自动访问市场供应商，不自动补交易、不创建备份，也不因浏览而连续生成后台任务。若复用的 Analytics 方法会维护快照，应明确区分轻量检查与用户启动的数据准备步骤，避免把现有隐式写入藏在新“只读检查”入口中。

### 3.2 数据准备：提示必须可以行动

问题以稳定的类型、日期范围和资产/账户身份组织。先区分“影响计算”“需要本人核对”“维护提醒”，不提供难以解释的综合健康分数。

| 问题 | 用户看到的说明 | 下一步 |
|---|---|---|
| 所选期间早于历史起点 | 当前仅覆盖哪些日期 | 调整范围；阅读覆盖说明 |
| 历史快照待更新 | 哪段期间尚未更新或需要重算 | 启动/继续现有快照重建，展示进度和失败 |
| 历史报价或 FX 缺失 | 哪个工具/币种在哪些日期无法估值 | 打开对应历史市场数据或手工录入入口 |
| 当前价格较旧 | 报价时间与来源 | 显式刷新或查看来源 |
| 手工资产很久未估值 | 最近估值日期 | 打开更新估值入口，或保留待办 |
| Residual 超过容差 | 哪个组件、哪些日期存在未解释差额 | 打开 Drivers 明细和相关 History |
| 没有最近备份记录 | 仅表示缺少备份状态证据 | 打开现有备份入口 |

重要规则：

- “今天刷新报价”不能当作修复“上个月缺少报价”。实时与历史来源必须区分。
- 有历史价格不意味着有历史持仓。不能向 History Origin 之前回填当前数量来制造历史曲线。
- 手工房产估值、定期更新余额与交易所报价的更新频率不同；不将统一 24 小时阈值套用到全部资产。
- 初版行情新鲜度复用已有来源/TTL 规则；手工估值只展示距今时间和明确的提醒阈值。提醒阈值不影响财务计算，不假装掌握各市场完整交易日历。
- Residual 按既有 component/day 容差处理；净额抵消仍应保留异常入口。
- 正常浏览和跳转不得把问题自动标为“已修复”。只有重新读取权威数据才能判定问题是否消失。

### 3.3 核对余额与持仓：先比较，再解释差异

用户对照银行、券商或自己的记录，输入或确认对应的截止日数值。第一版手工核对即可，不要求上传账单。

| 对象 | 核对项 | 不能混淆的内容 |
|---|---|---|
| 单币种现金账户 | 截止日原币余额 | 不用折算后余额掩盖原币差异 |
| 多币种账户现金 | 每个币种的原币余额 | 不把不同币种余额相加后判定一致 |
| 持仓 | 同一工具的数量，必要时查看成本依据 | 数量正确不等于市值、成本基础、收益都正确 |
| 手工估值资产 | 数值、币种、估值日期 | 这是本人确认的估值，不是外部成交价格 |
| 负债 | 同一截止日的未偿金额 | 数据录入保持原领域符号约定；净资产展示使用有符号贡献 |

系统值与外部值必须同日期、同币种、同对象。最新余额不能直接拿来核对历史月末；若外部记录只有其他日期，应调整核对日期或保留待核对。

历史数量必须来自该日期的账本重放或其他既有权威证据。不能使用“历史市值除以价格”作为持仓数量核对的权威值；若现有读模型未暴露历史数量，应补 application 读投影，而不是在 React 中反推。

比较使用精确十进制，分别遵守金额、原币金额和数量契约。显示四舍五入后相同不等于底层数值相同。若允许小差异，必须显式说明该比较规则；不能借用 Analytics residual 容差来自动宣告余额核对成功。

出现差异时，第一版提供以下选择：

1. 查看 History，寻找漏录或时间不符的活动。
2. 通过既有入口补录/更正活动。
3. 确认需要余额或数量调整，打开现有 reconciliation/adjustment 预览流程。
4. 暂不处理，写明原因并保留未解决状态。

**差额不能自动记成收入、收益或 Adjustments。** 未解释 residual 也不是一条可自动生成的调账金额。核对标记本身不创建或修改金融活动；用户确认的金融更正仍遵守既有历史可变更边界，不能绕过 Starting Point 或不可变 activity 规则。

### 3.4 本期结论与保存

复用最终 Asset Changes/Return Analysis 的数据，展示期初、期末、净变化和主要驱动，提供“查看计算口径”和对应分析页入口。

- 明确区分净资产变化、期间投资收益、当前累计浮盈和现金流。
- 页面说明当前范围、币种、截止日期与数据覆盖。
- 完成部分月份或保留待解决问题时，不能用“完整月份、全部核对无误”的措辞。
- 本轮不额外设计六套图表，不重新计算收益率。

保存时记录本次核对的范围、截止日期、核对项、保留问题、备注及依据版本。用户可以保存“仍有待处理事项”的记录，也可以保存无待处理事项的记录；两者应有清楚区分。

这不是锁账。以后仍可按现有规则补录和更正，旧核对记录保留，当前有效性重新判断。

## 4. 核对记录与后续变化

### 4.1 建议的数据模型

新增一个小型核对聚合，存入本地业务数据库，以便备份/恢复后保持一致。不要存放在纯前端 localStorage 或独立 sidecar 中。

以下是概念字段，具体命名和 migration 编号在实施时按届时 schema 确定：

| 数据 | 建议内容 |
|---|---|
| Review | household、期间、历史 timezone、范围、valuation、创建/保存时间、备注、替代的旧 review ID |
| Review item | account/holding/currency、核对日期、核对类型、权威值、用户参考值（可选）、结果、备注 |
| Open issue | 稳定问题类型、对象/日期、保存时状态、用户保留原因 |
| Review basis | 计算契约版本、所依赖输入的签名及最小来源身份，用于判断核对依据是否改变 |

保存后的核对版本保留原始记录；再次核对追加新版本，不静默覆盖先前“当时确认了什么”。草稿可以更新。初版不存账单附件，不要求外部机构账号、文件路径或原始金融文件。

Review 不成为第二套余额表，不参与净资产计算。保存的金额是核对证据，实际资产仍以既有账本和估值链路为准。

### 4.2 状态分成两个维度

不要把所有状态塞入一个互相冲突的枚举：

| 维度 | 建议状态 |
|---|---|
| 核对进度 | 草稿 / 已保存且有待处理事项 / 已保存且无待处理事项 |
| 依据有效性 | 与当前数据一致 / 相关输入已变化需复核 / 暂时无法验证 |

“相关输入已变化”表示原结论需要复看，不保证每个汇总金额都发生变化。“暂时无法验证”用于读取失败等情况，不能自动变成有效，也不能删除已保存记录。

### 4.3 补录后的变化提示

示例：

> 你补录了 8 月 12 日的活动。8 月核对所依据的数据已变化，相关分析需要重新查看。

可展示变动类型、对象和受影响日期，初版不保存所有分析中间结果，也不建设每次重算的完整差异历史。

有效性判断不能复用进程内 `analysisDataGeneration`，应用重启后也必须正确。建议第一版在打开已保存记录和确认保存时，计算与该核对范围相关的输入签名：

- 包括影响期初状态的历史活动、期间活动及更正链；不能只筛选本月新增活动。
- 包括所用快照及其 revision/来源、影响结果的估值与 FX 依据。
- 包括影响范围/计算的账户、工具、ownership 和 History Origin 元数据，以及计算契约版本。
- 不只比较最终总额：两笔抵消的更正也应使相关核对依据变化。
- 主题、窗口大小、无关的纯显示设置不应使核对失效；期间之后且不影响历史的普通活动也不应使旧月份全部失效。

这是一项明确需要实现测试的读模型契约，不应直接对整个数据库文件做 hash。读取应基于一致的数据视图；计算完成后保存时，必须在现有写协调机制内重新检查依据是否仍匹配，再原子提交核对记录。若输入改变，要求刷新，不保存一个被并发更正悄悄越过的“最新确认”。

初版按打开记录时检查即可，无需后台轮询全部月份。若后续性能证据要求缓存，再引入持久化 revision/dirty 范围优化；不能用遗漏关键输入来换速度。

## 5. 备份状态的表达

复用现有 LastBackupStatus 和备份操作，不新增一套备份文件或恢复协议。

- 显示最近记录的创建时间、文件名和创建时校验结果。
- 说明它是历史记录，不代表文件当前仍存在，也不证明包含刚保存的核对结果。
- 没有备份或备份较早时给出操作入口；不阻止用户保存核对记录。
- 可在保存后提供“现在备份”，必须由用户显式启动。
- 核对元数据进入数据库后，现有整库备份应包含它；升级、旧备份恢复、恢复后有效性重检都要覆盖。
- 独立测试位置的恢复演练列入发布验收，不覆盖真实数据库，不作为每月必做步骤。

## 6. 分阶段实施

本轮阶段用 M 前缀，与 Analytics Phase 1–6 区分。全部状态均为 Planned。

| 阶段 | 交付内容 | 依赖 | 退出条件 |
|---|---|---|---|
| M0 契约与贯穿 fixture | 冻结截止日、范围、核对/估值/收益含义；确定历史余额/数量读路径与输入签名 | Analytics 完成并修复关键问题 | 同一家庭 fixture 的人工预期明确；不得从被测代码生成期望 |
| M1 数据准备页面 | 问题列表、日期范围、操作跳转、快照重算状态、备份摘要 | M0 | 无自动网络/金融写入；常见问题能定位到对象和日期；失败可重试 |
| M2 账户核对 | 截止日余额/数量比较、差异入口、可恢复草稿；新增必要 review 存储 | M1 | 原币/日期/对象一致；更正仍走原预览流程；无差额自动入账；升级与旧数据读取通过 |
| M3 保存与复核 | 保存核对版本、待处理事项、输入签名有效性、补录后提示 | M2 | 重启后状态正确；历史更正能触发复核；并发保存不会确认旧依据；无关设置不触发失效 |
| M4 月度闭环验收 | 本期分析跳转、完整流程、备份恢复验证、三语言与原生验收 | M3 | 独立 fixture 全流程完成；本人完成一次实际月份核对并记录摩擦点 |

M1 完成后即可获得一个有用的数据准备入口；M2 能实际减少核对工作量；M3 才形成可长期信任的核对记录。M4 不是单纯“跑完单测”，需要本人验证流程是否适合自己的真实维护习惯。

### 实现约束

- 优先在现有 application/read-model 和 Wails 分层上增加窄接口，React 负责交互，不复制估值或收益公式。
- 页面概览采用有界批量读取，避免每个账户触发一次完整期间分析重放。
- 快照重建复用既有 31 天批次边界，正确处理部分完成、失败与继续；不得在长写锁中执行供应商网络请求。
- 迁移采用现有版本化流程，只增加本轮必需存储；升级后既有数据直接可读，不清库、不要求重新导入。
- 旧 schema 备份的兼容验证、恢复与升级继续由既有恢复契约负责；不能仅在新 review 表上测试空数据库。
- 所有新增交互包含 loading/empty/error/unavailable、三语言和键盘操作。

## 7. 验收 fixture 与测试矩阵

贯穿 fixture 至少包含两种币种、现金、同工具的两个账户持仓、一笔贷款和一项手工估值资产。记录工资、支出、内部转账、买卖、分红、还贷，以及一次中午实物转仓。

人工预期包含净资产、已知现金余额、持仓数量、哪些属于收益、哪些属于本金；复用 Analytics 的现有数学契约，不在本文定义新的收益公式。

| 场景 | 必须证明 |
|---|---|
| 月中开启 History | 只核对可覆盖期间，不把月初未知余额当零 |
| 缺历史价格、只有最新报价 | 刷新当前价格不会误报历史问题已修复 |
| 完全缺失/部分缺失/真实零 | 三者在比较、分析和核对状态中可区分 |
| 现金余额相同、持仓数量不同 | 不能仅凭总市值相同宣告全部核对完成 |
| 同一账户的两种币种 | 分别比较原币值，不做跨币种抵消 |
| 正负 residual 抵消 | 异常入口仍存在；不能自动以零净额结案 |
| 补录上月交易或更早的期初相关活动 | 已保存的受影响核对记录需复核，旧记录仍保留 |
| 两笔相互抵消的更正 | 即使最终总额不变，也能发现依据变动 |
| 调整发生在核对完成之后 | 保存时重检；旧版本不能被标成最新确认 |
| 新增无关的下月活动/更换主题 | 不让所有历史月份无差别失效 |
| 程序重启/恢复备份 | 不依赖内存 generation，核对数据与有效性可重新读取 |
| 保留未解决事项并保存 | 明确“有待处理事项”，不伪装为全部无误 |

自动测试覆盖 domain/application、SQLite 迁移与恢复、Wails DTO、frontend 比较/导航/状态；原生验收覆盖入口 → 问题处理 → 返回核对 → 分析 → 保存 → 重启。具体命令遵循 [本地开发流程](../development/local-workflow.md)，每阶段交付时分别报告自动测试和未执行的桌面检查。

## 8. 本轮不做什么

- 银行/券商自动连接、后台同步、定时抓取、自动上传账单。
- 强制锁账、会计期间封存、多角色审批、财务团队权限。
- 自动根据差额生成交易、工资、分红或收益。
- 通用账单解析平台、收据管理、逐笔消费预算、税务报告。
- 为生成月度摘要接入付费 LLM 或远程分析服务。
- 复杂提醒系统、月末定时任务和后台全库审计。

这些边界服务于单人维护成本。需要时可以另立计划，不通过本轮的数据问题入口顺便引入。

## 9. 本轮之后的候选方向

下面是此前讨论的后续方向，属于 Deferred，不是 M0–M4 的交付条件。优先级取决于完成一次真实月度核对后暴露的最大摩擦。

### 候选 A：本人常用机构的导入与对账

当手工整理账单成为主要耗时，先支持一家实际使用的银行或券商、一种文件格式。

目标包括保存字段映射、识别重复导入、展示新增/疑似重复/冲突、预览后写入、批次来源追踪。相同文件重复导入和不同文件重复覆盖同笔活动是不同问题；不能仅对整份文件做 hash 后就宣称业务去重完成。

**必须另立契约：** 当前 Accounts/Holdings CSV 是 create-only。未来流水导入、更新和匹配不能静默改变其行为。模糊匹配先给候选，不自动合并交易；原始文件不进入公开 fixture。第一步可以只做只读比对，证明能节省操作再做写入。

### 候选 B：资产可用性

当主要问题变成“资产里哪些近期能使用”，增加由本人设置的流动性/用途属性，例如随时可用、需要出售或赎回、长期锁定、不打算变现。

优先复用账户/持仓和现有 Group 概念，避免建立重复分类树。属性不改变账面价值，也不由模型根据名称猜测。第一版只回答当前构成，不做未来收益预测或投资建议。

### 候选 C：确定性的月度摘要

当数据与核对流程稳定后，按模板生成“资产变化多少，主要来自收入、支出、市场与汇率”的简短摘要。

完全复用 Go 权威金额和 coverage。未解释差额、部分期间和口径切换必须保留，不编造因果。可选导出 Markdown；无需 LLM、云端请求或额外 token 成本。

### 候选 D：搜索与常用视图

当找账户/交易比维护数字更耗时，优先补搜索和保存常用筛选。先保存本人常用的 scope/期间规则，避免与本轮 review evidence 或 Analytics 临时 session filters 混为一套状态。

推荐决策规则：**每轮解决一次真实维护中最耗时或最不可信的环节，再决定是否需要下一项能力。** 不把所有候选拼成下一轮的大型路线图。

## 10. 给实现者的交付约定

适用于后续使用 Luna 或其他模型实施：

1. 每次只接一个 M 阶段，先读取该阶段引用的现有接口和测试，再改实现。
2. 若数据读取不能支持既定财务语义，指出具体缺口并补窄读模型；不要在前端推导替代金额。
3. 修复测试前解释旧断言为什么错误；不能删断言、降低精度或隐藏缺失状态来换绿色结果。
4. 每阶段交接只保留：改动范围、关键契约、新增边界测试、实际运行结果、未执行 gate、下一阶段依赖。
5. 涉及计算依据、历史更正、数据迁移与恢复的批次进行独立差异审查；普通组件按已有模式实现。
6. 实施时以届时实际代码和最终 Analytics 契约为准，重新核对本方案的复用点；本文不锁定未来 schema 编号或发布版本。

本轮完成的产品标准是：**用户能够在一个连贯流程中核对一个真实期间，保留未解决问题，并在后来相关数据变化时知道需要重新核对。**
