# Nestworth 下一步功能设想

> 2026-09-20：第 1、8、9、12 条已落地首版；具体行为、范围和验证边界见 [实现说明](household-navigation-and-health.md)。下文保留提出需求时的背景。

这份清单对照当前产品表面（Overview、Accounts、Portfolio、History、Return Analysis、Asset Changes、Directory、Market Data、Data Health、Settings）和已有设计，尤其是 `docs/product/product-vision.md`、`docs/architecture/domain-model.md`、`docs/design/monthly-review-and-data-confidence.md`。它不是既有 roadmap 的复述，也不把“字段或 API 已经存在”写成“功能基本做完”。

今天的 Nestworth 已经能维护一份家庭资产负债表：账户与持仓、多币种估值、不可变 History、Dietz 收益、归因瀑布、显式行情同步。下一步的杠杆，是让用户信任眼前的数、少在页面间迷路、补上每天会卡死的录入缺口。任何一条如果还缺统计口径、历史数据规则或产品边界，都先写清楚，再谈实现。

**核心规则：** 后端算过、schema 有列、filter 能传，只说明有材料。真正要交付的，仍是用户能核对的口径、历史是否可回放、以及 Nestworth 故意不做的边界。

每条都写：**首版范围**、**不做什么**、**前置依赖**、**可验证的用户结果**。

---

## 怎么读这份清单

- **编号沿用原条目**，便于对照评审。
- **1 / 9 / 14 / 24 共用一份查询形状**，预设和临时导航分开存，不要发明三套状态。顺序是：带 scope 跳转并恢复现场 → 命名预设 → 命令面板。
- **Portfolio** 按 Domain Model：只加总 holdings 账户里的完整持仓，排除现金；`include_in_portfolio` 是未使用的兼容字段。
- **Contribution 的 unrealized** 明确不可用：分析内核还没有期间末成本基础。这不是下拉没开。
- **成员 filter** 只判断账户是否包含该 Member，不按 BPS 分摊金额，更不是成员个人回报。
- 产品不是报税、税 lot 优化、预算 App，也不是会在行情同步时默默改账本的系统。见 `docs/product/product-vision.md`。

## 共同导航上下文（1 / 9 / 14 / 24）

现在没有 URL。页面 id、Insights 过滤、区间、tab 活在当次 session。从 Overview 绕一圈或刷新窗口就会丢。账户、标的、activity、缺口都有稳定 ID，缺的是**一份可共用的查询形状**，外加分开保存的预设与临时导航，而不是 Overview 一套、Insights 一套、命令面板再一套。

查询形状共用一份，但**命名预设**和**临时导航状态**分开存，不要三个功能各写各的，也不要把一次跳转的滚动位置写进预设：

- **查询（预设可保存）：** 目标页、scope（household / account / instrument / 以后才加的 currency 与 asset_class）、完整 filters（含账户过滤）、是否含现金、估值方式、tab，以及**动态区间规则或固定日期**二者之一。
- **临时导航：** 来源页、返回位置、滚动位置。跳转必须能回来；回来时这些现场还在，但它们不属于预设。
- 命令面板只是打开查询、并带上当前这次临时导航的入口。

## 第一批：信任与录入维护

### 12. 让 Data Health 的缺口点到具体对象（最高优先级）

**今天：** Overview 的下一步把人送到 Market Data 或 Accounts，不会预选缺价的那只标的、缺估值的那个账户。Calendar 和 Drivers 上的 ◇ / partial 也多半只能“去 History 看看”。Repair 只覆盖可执行的行情/快照类问题。

**仍待设计：** 缺口类型还不能混成一颗绿勾。缺价、缺 FX、**行情待发布**、**快照待重建**、手工估值过期，修复路径不同；不是所有缺口都该进 Repair。行情尚未发布时，重建快照不能补出价格。不要使用含义不清的“快照待发布”。

**为什么重要：** 用户已经看见“不完整”，却找不到该修哪一条。信任先于再多一张分析图。

| | |
| --- | --- |
| **首版范围** | 每条缺口带上对象（Instrument / Account / FX pair）、影响的日期区间、缺失原因、点进去的落点，以及返回位置。缺价 → 该 Instrument 的报价或 Repair；缺 FX → 对应货币对；**行情待发布** → 对应市场数据状态、缺的日期、可重试条件（不是 snapshot 进度）；**快照待重建** → 重建任务；缺账户价值 → 该 Account 的更新表单。 |
| **不做什么** | 不把所有缺口塞进 Repair；不把行情待发布和快照待重建收成同一条路径；不写“快照待发布”；不把“当前报价已刷新”说成“历史缺口已补”；行情未发布时不把重建快照说成能补出价格；不发明综合健康分；点进去本身不把缺口标成已修复。 |
| **前置依赖** | Data Health / Market Data / snapshot 状态已经能区分类型。导航上下文用第 9 条的最小携带字段即可，不必等命名预设。 |
| **可验证的用户结果** | 从 Overview 或 Data Health 点一条缺价，打开的是那只标的、能看到缺的是哪段日期。点行情待发布，落到该标的/货币对的市场数据状态、日期和可重试条件，而不是重建任务。点快照待重建，落到重建任务；若对应日期行情仍未发布，重建不能把价格变出来。修完回来，仍停在原来的清单位置。 |

### 7. 把 Settings 里已经生效、但改不到的偏好亮出来

**今天：** `weekStart` 和 `dateFormat` 已经驱动 DatePicker 和 Return Calendar 的周起始，Settings 没有控件。Household 名称只在 Onboarding 写一次。Base currency 在 Settings 只读——这是对的。

**仍待设计：** 时区与 History Origin 时区的关系要写进文案，避免用户以为改了显示时区就改了账本日期。

**为什么重要：** 用户看见的日历行为像是系统替他们选的。改得到的偏好，才谈得上“这是我家的账本”。

| | |
| --- | --- |
| **首版范围** | Settings 可改 week start、date format、Household 名称。说明这些只影响显示与日历，不影响已入账金额。 |
| **不做什么** | **不顺手开放 base currency 编辑。** Base currency 在 Onboarding 之后不可变；改币种是单独的迁移设计，不是这个表单的一部分。 |
| **前置依赖** | 无分析口径依赖。不要和账户生命周期字段、inclusion flags 捆在一次“把 schema 亮出来”的改动里。 |
| **可验证的用户结果** | 在 Settings 把周起始改成周日后，DatePicker 和 Return Calendar 从周日开始；改 Household 名称后，各页标题立刻用新名字；base currency 仍然只读。 |

### 8. Directory 与 Accounts 对齐：能看见、能恢复已归档对象

**今天：** Accounts 有 Show archived。Members / Institutions / Groups 归档后从默认列表消失，没有对等开关。归档本身存在，恢复路径不对称。

**仍待设计：** 归档 Member 不改写已有 Ownership（Domain Model 已定）。恢复一个对象不会自动恢复关联对象——UI 要说清楚，不要让用户以为“恢复银行 = 恢复下面所有账户”。

**为什么重要：** 家庭成员改名、关掉的银行，过几个月一定还要找回来。找不回来，用户会怀疑数据删了。

| | |
| --- | --- |
| **首版范围** | Directory 三个列表都有 Show archived；已归档行能 Restore。默认列表仍然排除归档对象。 |
| **不做什么** | 不做永久删除；不把归档 Member 的 Ownership 改成别人；不级联恢复账户。 |
| **前置依赖** | 现有 archive / restore API。不依赖 Insights 导航。 |
| **可验证的用户结果** | 归档一个 Institution 后默认列表没有它；打开 Show archived 能看见并恢复；恢复后，原先引用它的账户仍在，不会凭空多出已归档账户。 |

### 11. 在加持仓时一并创建 Instrument

**今天：** Holdings 表单要先选已有账户和已有标的。Instrument 的创建、Yahoo / CoinGecko 搜索、贵金属模板都在 Market Data。Account 的 action sheet 已经能在账户上下文里建标的，Portfolio Holdings 还没有这条捷径。

**仍待设计：** 新建标的的 quote currency、quote preference、provider binding 仍走现有 Instrument 规则；捷径不能绕过“符号不是唯一键”。

**为什么重要：** 加一笔新仓要在两个页面之间跳，是每天都会碰到的摩擦，不是新分析能力。

| | |
| --- | --- |
| **首版范围** | Portfolio 加持仓（以及与 Account action sheet 对等的路径）可以搜索或创建 Instrument，再回到同一张加仓表。创建成功后预选新标的。 |
| **不做什么** | 不在这条捷径里发明新的定价模型；不默认绑定未验证的 provider；不把“建标的”做成静默自动建仓。 |
| **前置依赖** | 现有 Instrument 创建与搜索。不依赖 activity 导入。 |
| **可验证的用户结果** | 在 Portfolio Holdings 点加仓，能搜到或不存在时创建一只标的，创建后不必去 Market Data 再走一遍；新标的出现在 Household 的 Instrument 列表里，规则与 Market Data 创建的相同。 |

### 15. 导出 History 与 Insights，而不只是账户表

**今天：** JSON 可导出账户、持仓定义、完整业务历史、行情和当前状态摘要。归因瀑布、收益日历尚无专用报表导出。备份用于整库恢复。

**仍待设计：** 导出必须带 scope、显示货币、计算口径、完整性（complete / partial / unavailable）。缺数不能被写成 0。这不是报税底稿。

**为什么重要：** 本地账本如果带不走明细，用户会重新把权威放到表格里。先能带走 History，分析导出才有意义。

| | |
| --- | --- |
| **首版范围** | 先做 History 明细导出（日期、kind、账户、金额、货币、标的数量、关联 ID）。再做 Insights 只读导出：当前过滤下的 Return Analysis / Asset Changes 汇总，表头写明区间、scope、货币、口径、完整性。 |
| **不做什么** | 不暗示可用于报税或税 lot；不导出备份二进制当“分析表”；不把 residual 或缺失输入填成 0；不做税务字段。 |
| **前置依赖** | History 列表与 Insights 过滤已经稳定。导出文件用的 scope 应能复述第 9 条的上下文，但不必等命令面板。 |
| **可验证的用户结果** | 导出一段 History，表格行能对上页面上的 activity，并能追溯账户/标的。导出一段 Return Analysis 时，打开文件就能看见这是哪个账户、哪种货币、是否 partial；缺报价的日子不会变成 0% 回报。 |

## 第二批：接上已有能力

### 9. 从账户和持仓一跳进入 Insights

**今天：** Account 详情和 Holdings 表能打开账户，不能带着 account / instrument scope 打开 Return Analysis 或 Asset Changes。Insights 反过来也不能稳定回到账户详情。分析过滤已经支持这些维度，缺的是页面之间的手势和返回。

**仍待设计：** 跳转时的区间默认值（账户打开日？History Origin？当前 Insights 区间？）以及“没有覆盖期”时的空状态，要先定，不能 silently 用 0。

**为什么重要：** 这是共享导航上下文的第一步。做完以后，Overview 和预设才有东西可复用。

| | |
| --- | --- |
| **首版范围** | 从 Account / Holding 打开 Return Analysis 或 Asset Changes，Insights 能跳回来源账户。返回时恢复来源页（临时导航，不写进预设）。只做已经存在的 household / account / instrument scope。入口必须分清：账户内持仓 → `instrument scope + account filter`（当前这笔持仓，不是全家该标的）；Portfolio 跨账户标的汇总 → 仅 `instrument scope`。 |
| **不做什么** | 不从账户持仓行只带 instrument scope 跳走（两个账户都持有 NVDA 时，会把“这个账户的 NVDA”扩大成“全家庭的 NVDA”）；不在这一步发明 currency / asset_class 一等 scope（见第 5 条）；不并行做命令面板；不改回报公式。 |
| **前置依赖** | 第 12 条已能携带对象与返回位置更佳，但本条可以先定查询形状与临时导航的分工。 |
| **可验证的用户结果** | 同一标的（如 NVDA）分布在两个账户：从账户 A 的持仓行点“看回报”，Insights 是该 Instrument + 账户 A 过滤，不含账户 B 的仓。从 Portfolio 的 NVDA 汇总行进去，才是全家庭该标的。从 Insights 返回，还在原来的账户详情，滚动和来源页还在。刷新前至少能在同一次会话里来回。 |

### 14. 记住常用的分析切片

**今天：** Insights 的过滤、区间、tab 活在当次 session。没有 URL，也没有命名预设。

**仍待设计：** 预设存本地即可，但要写清：Household 切换或备份恢复后怎么办；预设引用的已归档账户如何显示。预设是视图，不是第二份账本。动态区间（今年、YTD、近 30 天）按打开时解析；固定日期按保存时的起止日，不再随日历滚动。

**为什么重要：** 用户真正的工作流是反复看“今年、这个账户、不含现金”。先能恢复现场，再给几次常用切片起名字。

| | |
| --- | --- |
| **首版范围** | 查询形状与第 9 条共用，但分开保存。**预设：** scope、完整 filters、是否含现金、估值方式、tab，以及动态区间规则或固定日期。**临时导航：** 来源页、返回位置、滚动位置。先做“离开再回来不丢”（临时导航）；再做少量命名预设，打开时套上查询、不恢复过期滚动。 |
| **不做什么** | 不把返回位置或滚动写进预设；不把“今年”存成打开当天的绝对日期；不另做 Overview 专用状态、不另做命令面板收藏夹；不把预设写进财务库当权威事实；不做云同步。 |
| **前置依赖** | 第 9 条的查询形状 + 临时导航分工。 |
| **可验证的用户结果** | 设好“今年 / 某账户 / Return Analysis / Contribution”，去 Overview 再回来，过滤还在，滚动作为临时状态恢复。保存“今年”预设后，跨年再打开解析为新一年；保存固定日期的预设，跨年后起止日不变。 |

### 1. 让 Overview 成为真正的家庭仪表盘

**今天：** Overview 给出净资产、资产/负债、按 Institution / Account Type / Member / Group 的构成，以及数据健康与下一步。数字是静态的。点构成行进不了 Account、Portfolio 或 Insights。`NetWorthTrend` 已经能按 30d / YTD / 1y / all 返回，Overview 没有趋势图——趋势只出现在 Portfolio 的持仓小计上。

**仍待设计：** Overview 趋势是净资产口径，Portfolio 趋势是持仓小计，两者不能画成同一条线而不加说明。点 Member 行只能进入“与该成员相关的账户”，不能假装已经有成员个人回报（见第 6 条）。

**为什么重要：** 打开应用第一眼仍是一张当前快照。用户最常问的是：这个月变了多少、现金和投资分别在哪看、点某一类能往下钻。

| | |
| --- | --- |
| **首版范围** | 净资产趋势（沿用已有区间）；构成行可跳到账户列表或第 9 条的 Insights scope；数据健康沿用第 12 条的带对象跳转。文案区分净资产变化与投资回报。 |
| **不做什么** | 不在 Overview 重算 Dietz；不把 Portfolio 持仓趋势冒充净资产；不把 Member 构成行做成“该成员个人回报”；不新开第三套状态。 |
| **前置依赖** | 第 9 条跳转；第 12 条缺口落点；第 3 条的差异说明（可同期做）。 |
| **可验证的用户结果** | Overview 能看见这段时间净资产怎么走；点某个 Institution，落到该机构下的账户；点数据健康条目，落到具体标的或账户。数字旁边能读到这是净资产，不是 Portfolio 持仓收益。 |

### 2. 把已经算好的收益放到它该出现的地方（收窄）

**今天：** Holdings 表展示成本、市值、未实现盈亏。Account 详情只显示持仓市值。后端已按账户、持仓给出 realized / unrealized / dividend，并把未实现拆成 `instrumentMovement`（价格）和 `currencyMovement`（汇率）。这些是**当前时点**的成本与累计未实现，不是期间回报。Contribution 的 unrealized 空状态已写好，下拉里没有这一项——因为分析还缺期间末成本基础，不是漏开了一个选项。

**仍待设计：** 期间末未实现（区间结束日的市值 − 当日剩余成本）是单独的后端能力，要历史成本回放与 snapshot 对齐。在此之前，任何“期间未实现”下拉都会把当前累计数误当成这段时间赚的。

**为什么重要：** 用户在某个券商账户或某只股票上，确实想看见成本和浮盈。但把当前浮盈当成“这段时间的回报”，Insights 就和账户页在说两套话。

| | |
| --- | --- |
| **首版范围** | 只在 Account / Holding 上展示**当前成本**和**累计未实现**（已有分解可以显示价格 vs 汇率）。期间回报只去 Insights 的 Return Analysis。文案写明：这是现在的浮盈，不是本月/本年回报。 |
| **不做什么** | 不启用 Contribution 的 unrealized 下拉；不用 `总回报 − 已实现 − 分红` 去凑未实现；不把账户回报乘上所有权百分比；不把“打开下拉”当成期间末未实现已经交付。 |
| **前置依赖** | 现有 GainService 的当前读模型。期间末未实现另立后端设计后再回到 Insights。 |
| **可验证的用户结果** | 打开账户能看见该账户持仓的当前成本和累计未实现；点“看这段时间赚了多少”进入 Insights，数字与账户页的浮盈可以不同，页面解释了为什么。Contribution 仍然没有未实现选项。 |

### 3. 说清楚 Overview 和 Portfolio 为什么对不上（收窄）

**今天：** Overview 是纳入净资产的全部账户（含现金、负债、房产等 manual value）。Portfolio 只加总 holdings 账户里的持仓，**故意排除现金腿**。`include_in_portfolio` 和 `include_in_liquid_assets` 存在于 schema，表单故意不展示：Portfolio **并不读**前者，后者也还没有对应指标。这是 Domain Model 里的兼容字段，不是“差一个开关”。

**仍待设计：** 若以后要“自定义投资宇宙”，那是新的 portfolio-scope 设计：改配置后历史回报是否重算、已保存的 Insights 预设怎么办、与 `include_in_net_worth` 如何并存。不能靠重新点亮旧 flag 代替设计。

**为什么重要：** 两个大数字并排出现在侧栏，差一笔现金或一笔负债就会让人怀疑估值错了。先解释差异，比给一个会改历史口径的开关更重要。

| | |
| --- | --- |
| **首版范围** | 两页都写清范围：Overview = 家庭净资产；Portfolio = 持仓市值，不含现金、负债、无持仓的投资账户。提供从一侧钻到另一侧（现金去账户/Overview，持仓去 Portfolio）。 |
| **不做什么** | **不重新启用 `include_in_portfolio` / `include_in_liquid_assets` 作为实现理由。** 不把“用已有 flag”写成这期工作。不做自定义宇宙。不把现金静默加进 Portfolio 来“对上数字”。 |
| **前置依赖** | 第 1 条的构成跳转、第 9 条的钻取。流动性口径见第 20 条，不在这里顺手做。 |
| **可验证的用户结果** | 用户能在 UI 上读到：两边不一样是因为范围不同。从 Portfolio 的差额说明能点到被排除的现金账户；没有出现“计入投资组合”复选框。 |

### 24. 命令面板：在本地账本里跳到任何东西（同一轨道最后做）

**今天：** 十个顶级页面，分析状态只活在内存，没有全局搜索。

**仍待设计：** 搜索要覆盖哪些对象、已归档是否默认可见、缺口条目如何排序。它必须复用第 9 / 14 条的上下文，而不是第三套状态。

**为什么重要：** 桌面产品里，键盘跳到账户、标的、未修缺口、某段 Insights，比再加导航项更能降低负担。但先没有可恢复的跳转，面板只是更快地迷路。

| | |
| --- | --- |
| **首版范围** | 打开账户、标的、History activity、Data Health 缺口、已保存的 Insights 预设。打开预设只套查询形状；来源页 / 返回 / 滚动走临时导航，不写进预设。 |
| **不做什么** | 不在预设和跳转还不稳定时先做面板；不执行入账或 Repair；不搜索成“迷你分析引擎”。 |
| **前置依赖** | 第 9 条跳转 + 第 14 条预设 + 第 12 条缺口身份。 |
| **可验证的用户结果** | 用键盘打开某账户或某条命名切片，落地状态与从页面点进去相同；Esc 回到上一个现场。 |

## 第三批：降低长期维护成本

### 4. 导入真实流水：统一模板，而不是 Record API 的批包装

**今天：** 已移除 CSV，JSON 仅支持导出。History 要一条条 `buy` / `sell` / `cash_in` / `cash_dividend` / `cash_transfer`…… Preview、Record、Fix、Undo、请求级幂等已经是完整契约。备份能带走全部 activities，表格进不来。

**仍待设计（导入是新设计，不是现有 Record 的 for 循环）：**

- **History Origin：** 导入发生在 origin 之后，还是要把 origin 推得更早？更早的导入是补历史，还是改起点？
- **去重：** 券商文件去重（外部流水 ID、日期+账户+金额+数量）与请求幂等（`ActivityMutation` key）不是同一件事。
- 日期重叠、同一天多笔同方向成交。
- 转账对手方、费用、货币、时区（文件时区 vs History Origin 时区）。
- 预览对现金 / 持仓 / 成本的影响，以及**整批 Undo**（仅当没有后续依赖交易；见下）。
- v1 不接任意券商格式。

**为什么重要：** 家庭账本的冷启动成本几乎全在历史成交。没有 activity 导入，Insights 和成本都要从零手敲。高价值，但不能抄近路。

| | |
| --- | --- |
| **首版范围** | 一份 Nestworth 统一模板；限定 activity 类型（建议先：buy / sell / cash_in / cash_out / cash_dividend / cash_transfer）。预览每行将如何改现金、持仓数量和平均成本；确认后批量入账。整批 Undo **仅在没有后续依赖交易时**成立。错误按行报告。 |
| **不做什么** | 不当成“循环调用 Record API”；不接券商对账单原格式；不在预览里自动修 Origin；不静默合并可能重复的行；不把导入当银行直连；**不无条件保证 Undo 能回到导入前**——导入后若已卖出持仓或转走现金，应阻止撤销或走纠正（Fix / 冲正）流程。 |
| **前置依赖** | Preview / Record / Undo 契约。History Origin 规则必须先写进导入说明。第 15 条的导出格式最好与模板同一套列，避免来回翻译。 |
| **可验证的用户结果** | 用模板导入十几笔买卖和一笔转账后，现金、持仓、成本与手工记同样的几笔一致；故意重复导入同一文件会被预览标成冲突，而不是再入一遍。导入后没有后续依赖时，Undo 整批，持仓和现金回到导入前。导入后又卖掉其中一笔持仓或转走现金，整批 Undo 被阻止或只能纠正，不能把账悄悄拧回导入前。 |

### 17. 落地已有的 Monthly Review 设计（不是“结账”）

**今天：** 产品已有 History Start、每日 snapshot、dirty range、Data Health、Asset Changes 的收入/支出/费用/投资回报分类。缺的是按已有设计做的那次维护闭环，不是新的会计关账。

本条**实现** `docs/design/monthly-review-and-data-confidence.md`，不要另写一套“每月结账”。该设计已写明：不是强制月末任务、不是日常记账、不是预算或 accounting close；“没有缺价”、“用户核对过余额”、“备份在创建时校验过”是三种证据，不能收成一颗“数据全对”。

**仍待设计：** 设计本身仍是 Planned，不是实现声明。首版按该文档取最小切片。持久保存与“依据变更后失效提示”必须同一期交付，避免保存了会过期、却仍显示有效的结论。首版不单独做保存。

**为什么重要：** 家庭需要定期问“这些数现在信不信”，但“结账”会暗示锁账、关月、账对了。报价齐全 ≠ 用户的账是对的。

| | |
| --- | --- |
| **首版范围** | 按该文档：某个 as-of 日的缺口清单 + 账户核对（现金、持仓数量、手工估值）。默认上一个完整日历月，但用户可在月中复盘最近一个 closed day。不锁期。不持久保存复盘结论。离开页面后，本次核对的勾选/备注只作为会话内临时状态保留（或明确丢弃）；下次打开不把它当成已确认的月度结论。 |
| **不做什么** | 不强制月末；不 period lock；v1 不保存复盘记录，因此也不做“已保存且仍有效”的展示；不自动把差额记成收入/回报/Adjustments；不把行情完整说成账本正确；不做银行对账单匹配；不新开第二套分析引擎。 |
| **前置依赖** | 第 12 条的缺口身份与落点；Insights 已在用。**持久保存 + 依据变更后失效提示**作为同一后续切片一起交付，不把保存先上、失效后补。 |
| **可验证的用户结果** | 选定一个日期后，能看到哪些账户要对、哪些标的缺历史价；现金按原币核对，两个币种不能对冲成“已对齐”。v1 没有“保存带未决项 / 本月已结清”的持久记录。离开后再打开，看不到一条仍标成有效的过期结论。 |

### 18. 记录模板与草稿，而不是自动周期入账

**今天：** `cash_in` / `cash_out` / `cash_dividend` / `debt_payment` 都是一等 activity。没有“像上次那样”，没有草稿。Categories 已能按收入和支出汇总，每一笔仍要手填。

**仍待设计：** planned ≠ posted。自动按节奏入账是另一个项目：要处理错过的月份、金额变化、与 History Origin 的关系，以及绝不能在浏览时静默过账。

**为什么重要：** 家庭账本的日常密度在薪资、房租、还款上，不在偶然买股。先降低重复填写，再谈自动化。

| | |
| --- | --- |
| **首版范围** | 复制上一笔、命名模板、pending draft（可改、可丢弃、过账前不是财务事实）。覆盖常见现金与债务 kind。 |
| **不做什么** | 不做自动 recurring posting；不在到期日自己记一笔；不把草稿算进净资产或 Insights。 |
| **前置依赖** | 现有 Preview / Record。不依赖第 4 条导入，但模板字段应与统一导入模板能对上。 |
| **可验证的用户结果** | 点“与上月工资相同”得到一份可改预览，确认后才入账；未确认的草稿在 Overview 和回报里都不出现。 |

## 第四批：单独验证与设计

这些不是“把已有字段打开”。每一条都先有口径或边界，再写代码。

### 6. 家庭成员：先“相关账户”，后才是个人份额回报

**今天：** 账户所有权用 BPS。Overview 已按 Member **加权拆当前净资产**。Insights 的 More filters 可以按 member 过滤——**只检查账户是否包含该成员，不按 BPS 分摊期间金额或现金流**。Accounts 列表的 `ownershipScope`（sole / shared）在 API 里存在，列表没有这个开关。点 Member 行也不会进入该成员的收益，而且现在也还没有“该成员个人回报”这个指标。

**仍待设计（个人份额回报是独立设计）：** 已有所有权历史观察；历史回放也会读取它。缺的不是时间轴，而是成员回报如何消费这些事实：如何按历史份额分摊价值、现金流，以及处理份额变动。共同账户的外部流入算谁的、回报资本怎么取，也要一并写清。**禁止**用账户回报 × 所有权百分比冒充成员回报。

**为什么重要：** 产品定位是 household。共同账户、个人账户、谁的养老金，是家庭产品该讲的故事。但“过滤到相关账户”和“算出属于这个人的回报”不是同一件事；把前者当成后者，数字会看起来很完整，口径却是错的。

| | |
| --- | --- |
| **首版范围（阶段 A）** | 从 Overview Member 行进入“包含该成员的账户”列表；Accounts 可用 sole / shared；Insights 成员过滤的文案写成“相关账户”，并说明金额仍是账户全额，不是个人份额。 |
| **阶段 B（另立设计）** | 成员个人份额回报：如何按已有的历史份额观察分摊价值与现金流、份额变动日如何切段、与 Overview 当前加权净资产如何并列展示。 |
| **不做什么** | 不把账户 Dietz × BPS 当成成员回报；不在阶段 A 画“我的今年收益”；不改 Ownership 必须精确到 10000 BPS 的规则；不把“没有所有权历史”写成现状——历史观察已经在，缺的是回报如何用它。 |
| **前置依赖** | 阶段 A 依赖第 9 条跳转和第 1 条构成行。阶段 B 依赖阶段 A 的预期已经说清楚，以及成员回报如何消费已有的 dated ownership observations（历史回放已在读这些事实）。 |
| **可验证的用户结果** | 阶段 A：点某成员只看到有其名字的账户；一个 50% 的共同经纪账户在 Insights 里仍是该账户的全额回报，页面写明这一点。阶段 B 未做之前，任何地方都不会出现“张三 +12%”。 |

### 5. 货币与资产类别可以当分析对象，但先分清在滤什么

**今天：** 分析内核支持 scope：`household` / `account` / `currency` / `instrument` / `asset_class`。Contribution 可以按 currency、asset_class 分组。Filter bar 的主 scope 只有 Portfolio / Account / Instrument；currency 和 asset_class 缩在 More filters 里，当过滤条件而不是分析对象。

**仍待设计：** “USD 计价的资产”不是“USD 风险暴露”（股票报价 USD、成本 SGD、对家庭 base 的 FX，是三件事）。**过滤货币**和**显示货币**必须分开。原生多币种宇宙拒绝 native 估值时，不能假装已经有一套 USD 风险模型。

**为什么重要：** 多币种家庭确实会问“美元仓怎样”“股票 vs 现金”。内核切过这些 universe，不表示口径已经能对用户讲清楚。

| | |
| --- | --- |
| **首版范围** | 先用快捷切片验证：例如“报价货币 = USD 的持仓”“asset class = equity”，每条切片写明过滤货币 vs 显示（base）货币。通过后再考虑把 currency / asset_class 升成一等 scope。 |
| **不做什么** | 不把 USD 过滤说成美元敞口或对冲后风险；不在快捷切片未验证时改 Filter bar 信息架构；不引入多跳 FX。 |
| **前置依赖** | 第 9 / 14 条的上下文必须能表达这些切片，避免 Insights 内另做一套。第 3 条的 Portfolio 范围文案已经能区分现金与持仓。 |
| **可验证的用户结果** | 打开“USD 计价持仓”切片，列表里都是报价货币 USD 的标的，收益仍按 Household base 显示，标题能读出这两件事不同。加入一只报价 HKD 的标的后，它不会因为换汇成美元市值而进入该切片。 |

### 10. 只补真正有人用的账户字段

**今天：** `openedOn` / `closedOn` 在模型和校验里存在（关闭不能早于开户），创建/编辑表单没有。Institution 的 country/website、Group 的 color/description 同样落在 schema 里，Directory 只编辑名称、类型、图标。

**仍待设计：** 开闭日要先有归档、录入限制、历史统计规则：关闭后还能否记 activity？Overview 是否排除已关闭但未归档的账户？趋势是否从 `openedOn` 起算，还是从 History Origin？没有这些规则，把日期放进表单只是 schema 补全。

**为什么重要：** 目录产品需要一点厚度，但“列存在”不是用户任务。

| | |
| --- | --- |
| **首版范围** | 先写开闭日与 archive、History、净值统计的关系；规则成立后再在账户表单暴露这两项。Institution / Group 的附加字段只在有明确展示用途时再做（例如机构官网链接），不为齐字段而齐。 |
| **不做什么** | 不为 schema 完整而扩大表单；不把 `openedOn` 当成 History Origin；不在规则未定时刻统计“今年新开账户收益”。 |
| **前置依赖** | 第 8 条的归档可见性。历史统计规则 ideally 与第 17 条 as-of 核对一致。 |
| **可验证的用户结果** | 若开放闭日：关闭日之后不能再为该账户预览入账，或明确只能走归档/调整路径；Overview 对已关闭账户的处理与文案一致。没有规则之前，表单里仍然没有这两个日期。 |

### 13. 报价历史上的公司行为线索（只读）

**今天：** Tiingo 历史已经把 `split_factor`、`dividend_cash` 写进 `instrument_quotes`。Quote History sheet 只画价格序列和 observation kind。

**仍待设计：** 报价上的分红**不能证明**现金已到账，也可能和手工/导入的 `cash_dividend` 重复。拆股因子是行情观察，不是持仓数量已经按比例调整。

**为什么重要：** 用户看到拆股日价格跳崖，需要一个诚实提示。提示停在行情侧，账本仍然只承认已入账的 activity。

| | |
| --- | --- |
| **首版范围** | 在 Quote History 里只读展示拆股 / 分红线索（日期、因子、dividend 金额、来源）。可从持仓或 Data Health 跳到该日线索。 |
| **不做什么** | 不调整数量或成本；不自动记 `cash_dividend`；不把线索画成 History 里的 activity；行情同步仍然不得改账本。 |
| **前置依赖** | 报价里已经有这些字段。不依赖第 16 条。 |
| **可验证的用户结果** | 拆股日在行情图旁能读到 split factor；同一天如果用户没有记过分红，History 里仍然没有分红。线索文案不出现“已到账”。 |

### 16. 待确认的公司行为入账（与第 13 条分开）

**今天：** 平均成本回放处理买、卖、转入转出。拆股因子和现金分红随行情写入，成本引擎不消费它们。行情图在拆股日跳崖，持仓数量和单位成本不会自己对上。

**仍待设计：** 这是独立的 “pending corporate actions” 产品，不是把第 13 条的线索“确认一下”。需要：预览受影响的持仓以及数量 / 成本 / 现金；重复确认（行情分红 vs 已有 `cash_dividend`）；Undo；来源修订（行情日后改正）。**Price sync 在任何情况下都不得隐式改账本。**

**为什么重要：** Market Data 和 Ledger 是两套事实。收成一套只能通过用户确认的 activity，不能通过同步任务。

| | |
| --- | --- |
| **首版范围** | 待确认队列：从线索生成预览（哪些账户的哪些持仓、数量怎么变、现金是否增加、平均成本怎么走）；用户确认后才按现有 Preview / Record 入账；支持 Undo；来源被修订时，已入账的保持可追溯，待确认的要失效重做。 |
| **不做什么** | 不在 sync / Repair / 重建 snapshot 时写 activity；不把报价分红当作已收现金；不静默合并重复分红。 |
| **前置依赖** | 第 13 条只读线索先存在，用户已经习惯“这是行情，不是账”。第 4 条的去重思路（外部来源 vs 请求幂等）要复用，不要第三套去重。 |
| **可验证的用户结果** | 同步一只刚拆股的标的后，持仓数量不变，只出现待确认预览；确认后数量与成本按预览变化，History 多出可 Undo 的记录。再同步一次不会再入一笔。 |

### 19. 房产、贷款、保险的关系（后做）

**今天：** 账户矩阵里已有 `property` / `vehicle` / `insurance_policy`（manual value）和 `loan` / `credit_card`（balance，配合 `debt_draw` / `debt_payment`）。它们彼此不关联。家庭净资产已经把资产和负债两边都算进去了。

**仍待设计：** 链接的意义是解释房屋净值、月供与估值如何一起看，**不是**再减一次已经出现在负债里的贷款。保险不应复用“房产 − 贷款”模型：保单现金价值、保额、受益人，都不是抵押关系。

**为什么重要：** 用户想看“这套房还剩多少权益”。做错就会把负债减两遍，净资产立刻错。

| | |
| --- | --- |
| **首版范围** | 先做可选链接：某笔 loan 说明它关联某套 property / vehicle，用于展示估算权益（资产估值 − 已在负债侧的该贷款余额）。保险只做独立 manual value，不进这个模型。 |
| **不做什么** | 不在 Overview 里因链接再减一次贷款；不把保险保额加进净资产；不做抵押登记或还款摊销引擎。 |
| **前置依赖** | 第 3 条范围文案已经分清净资产与投资持仓。负债符号规则保持 Domain Model 的 `balance_sheet_role`。 |
| **可验证的用户结果** | 一套房产 + 一笔已计入负债的房贷，净资产与现在一致；详情里能看到“估值 − 该贷款 = 权益”。保险账户仍是单独的 manual value，不会出现“减去某笔贷款”。 |

### 20. 流动性：先定义口径，再谈应急月数

**今天：** `includeInLiquidAssets` 已按账户类型给默认值，写入 schema 和 JSON 导出，但没有任何页面汇总它。账户级布尔值表达不了一笔账户里同时有现金、股票和锁定期。

**仍待设计：** “能用的钱”要先有命名口径（哪些现金、哪些持仓要卖、哪些锁定）。应急月数还依赖可靠的必要支出基数——Categories 里的 spending 不是自动的“生活必需”。账户级 flag 不能表达账户内部结构。

**为什么重要：** 家庭决策经常问能用的钱，不是净不动产。用错 flag，只会多一个和净资产一样让人不敢信的大数。

| | |
| --- | --- |
| **首版范围** | 先写出口径文档：流动资产包含什么、按原币还是 base、持仓要不要折价、锁定如何标记。口径稳定后再考虑展示总额。应急月数另做：先有用户确认的必要支出，再除。 |
| **不做什么** | 不把 `include_in_liquid_assets` 重新点亮当成流动性产品；不在账户上用一个布尔表达现金 vs 股票 vs 锁定；不把 Categories 支出直接当应急分母。 |
| **前置依赖** | 第 3 条已经向用户解释过 Portfolio 不含现金。Domain Model 仍把该 flag 标成兼容、不读入任何合计。 |
| **可验证的用户结果** | 口径文档能用一个同时有现金和股票的经纪账户讲清楚：有多少算流动、有多少不算。在此之前，UI 不出现“流动资产 = …”的头条数字。 |

### 21. 先承认各类型怎么定价，再谈专用模型

**今天：** Instrument 已区分 `bond` / `mutual_fund` / `bank_investment_product`，行情路径基本按股票或手工价处理。没有票息、净值、摊余。选了 Bond 并不表示按债券计价。

**仍待设计：** NAV、票息、摊余成本是三个设计，不是一个“特殊定价”功能。每一种都要回答：谁是权威观察、缺观察时是 incomplete 还是拒绝、是否写入 History。

**为什么重要：** 中间态会让人以为类型已经带来了计价。先诚实，再加模型。

| | |
| --- | --- |
| **首版范围** | 按类型写清：当前支持的定价（手工盯市 / 通用行情）、不能自动做的事。Bond / 基金 / 理财在 UI 上标明“按你输入的价格或通用行情，没有票息或摊余”。 |
| **不做什么** | 不做统一的“特殊定价”开关；不在本条顺手做 NAV 历史、票息入账、摊余；不让类型选择改变已经入账的成本规则。 |
| **前置依赖** | 无。可与第 11 条创建标的时的文案一起出现。 |
| **可验证的用户结果** | 新建 Bond 时，用户能读到它不会按到期收益率计价；手工改价后市值变化，History 里没有自动票息。 |

### 22. 先做同一口径的上一段对比，再谈市场基准

**今天：** Return Analysis 有 Calendar、累计/环节趋势、贡献，没有基准，也没有“相对上一段”。内核按日给出 Dietz 和归因桶。

**仍待设计：** 市场基准要先定货币、日期对齐、是否含分红、缺数日怎么处理。“现金”必须有显式定义：账户现金腿、某种货币的现金资产，还是 0% 的名义线？不同定义会改变“跑赢现金”的结论。

**为什么重要：** 家庭常问的是比自己上一段如何、有没有跑赢现金。先把同一口径的两段时期放在一起，比接入指数更安全。

| | |
| --- | --- |
| **首版范围** | 同一 scope、同一货币、同一回报定义下，对比上一期间（上月 / 去年同期 / 上一段等长区间）。两边都展示完整性；一段 partial 时不能只报“超额”。 |
| **不做什么** | 首版不接市场指数；不把未定义的“现金”画成基准线；不在缺报价日用 0 填回报再比。 |
| **前置依赖** | 第 9 / 14 条能恢复同一 scope。第 2 条已经把期间回报留在 Insights。第 5 条的货币含义不能和基准货币打架。 |
| **可验证的用户结果** | “这个账户今年 vs 去年”两条 Dietz 并排，scope 和货币相同；去年缺两个月行情时，对比结果标成不完整，而不是一个漂亮的超额百分比。 |

### 23. 可选 lots：先收集平均成本服务不了的案例

**今天：** 成本只有平均法。平均成本回放**已经**支持部分卖出和转入转出：减仓按剩余数量保持平均成本，转出按转出时的平均成本走。Ledger 是不可变 activity，但这不等于已经有完整的 lot 历史——没有 `LotRef`，也没有 FIFO 身份。

**产品边界：** `docs/product/product-vision.md` 明确排除报税和税 lot 优化。不可变流水不是做 lots 的理由。

**仍待验证：** 哪些真实家庭场景是平均成本讲不清的（例如指定某笔转入的成本、同一标的多账户合并后再拆回、赠与）。没有案例就不要为“模型替用户做了选择”重写 Replay。

| | |
| --- | --- |
| **首版范围** | 不实现。收集平均成本无法服务的具体案例，写进后续验证。若以后做：**只做持仓 lot 追踪**（数量与成本身份），仍由用户确认。 |
| **不做什么** | 不做税务规则、申报表、tax-lot 优化、洗售；不把 lots 伪装成当前平均成本的“高级显示”；不因为 activity 不可变就声称 lot 历史已完备。 |
| **前置依赖** | 第 2 条的成本展示已经让用户看见平均成本；第 4 条导入不会偷偷写成 lot。Domain Model 仍把 FIFO lots 标为 deferred。 |
| **可验证的用户结果** | 现阶段：部分卖出后，剩余数量的单位成本仍是平均成本，与文档一致。若将来做 lot：卖出可以指向某批数量，Insights 与报税仍不出现税务字段。 |

## 刻意没放进来的

- **银行直连、后台自动刷新、多设备同步：** 刷新保持用户触发；核心浏览离线可用。那是另一条产品曲线。
- **把 Nestworth 做成预算 App：** Categories 已能看见 spending / income，账本的权威对象仍是资产负债表和不可变 History。预算若要出现，只能长在 Monthly Review 的维护闭环上，不应反客为主。
- **报税、税 lot 优化、税务导出：** 与产品愿景冲突；第 15、23 条都不得借道。
- **改 Household base currency：** 独立迁移，不从 Settings 偏好或导入顺手打开。
- **行情同步改账本：** 拆股、分红、NAV 纠正都不得在 sync 里变成 activity。
- **为了图表而图表：** Return Analysis 和 Asset Changes 已经相当密。优先打通信任、跳转和录入，而不是再开一张分析页。
