# Nestworth 功能现状与交互设计说明

> 文档状态：交互设计原型前置说明
>
> 更新时间：2026-08-25
>
> 适用对象：交互设计师、视觉设计师、产品负责人、后续前端实现人员

## 1. 文档目的

这份文档用于帮助设计师理解 Nestworth 当前已经具备的产品能力、核心概念、用户流程和设计问题，然后在此基础上制作信息架构、交互流程、线框图、高保真稿和可点击原型。

设计目标不是简单地把现有 Fyne 页面换一种颜色，而是重新检查：

- 用户是否能快速理解家庭资产负债情况；
- 用户是否知道应该从哪里添加和维护财务信息；
- 账户、成员、机构、分组、投资持仓和交易记录之间的关系是否清楚；
- 当前值、历史变化、投资收益和汇率变化是否被正确区分；
- 加载、空数据、数据过期、网络失败和部分不可用时，界面是否仍然可信；
- 简单用户能否快速完成基本操作，而高级功能不会一开始就造成负担。

这不是后端技术设计文档。设计师不需要了解 SQL、迁移实现或 Go 代码细节，但需要理解这些实现对用户体验造成的约束。

## 2. 一句话产品定位

Nestworth 是一个 local-first 的个人或家庭资产负债表应用，用于持续了解家庭拥有、欠付和持有的资产，以及这些财富随时间发生的变化。

它不是：

- 日常记账或预算应用；
- 银行或券商的权威余额系统；
- 交易执行终端；
- 税务申报或税务优化工具；
- 必须注册云账户才能使用的在线服务。

## 3. 目标用户

主要用户包括：

- 想了解个人整体净资产，而不想只看单个银行账户的人；
- 夫妻或家庭，需要表达共同持有和个人持有关系的人；
- 有现金、投资、负债、多种货币资产，需要定期维护的人；
- 希望数据保存在本地、可以离线使用，并且不依赖云服务的人。

用户通常愿意定期维护重要余额，但不一定愿意像记账软件一样记录每一笔消费。因此，产品应优先帮助用户建立可信的财富全景，再逐步提供历史和投资分析能力。

## 4. 当前产品原则

### 4.1 Household first

所有数据属于一个 Household。Household 可以是一位用户，也可以是一对夫妻或一个家庭。

### 4.2 Local first

本地 SQLite 数据库是事实来源。网络市场数据只用于用户明确触发的报价或汇率刷新，网络不可用时不能阻止用户打开和维护本地数据。

### 4.3 Financial correctness first

金额使用精确小数；所有权比例必须准确；负债、汇率、当前值和历史变化不能被界面静默猜测或修正。

### 4.4 Progressive complexity

添加一个普通银行账户应该很简单。成员所有权、投资持仓、交易历史、成本基础和收益分解等高级概念，应在用户需要时出现，而不是在第一次进入应用时全部展开。

### 4.5 Explainable data

每个重要数字都应尽可能让用户知道：它是什么、属于哪个范围、更新时间是什么、是否来自手工输入、是否因为缺少数据而不可用。

## 5. 当前功能状态

以下内容以当前 Go + Fyne 仓库的代码和 active release 文档为依据。设计阶段必须继续区分“当前已经实现”和“未来可能实现”，不能把历史资料或规划内容当成现有功能。

### 5.1 v0.1.1：家庭资产负债表

当前已实现的核心能力包括：

- 创建 Household 并完成首次设置；
- 创建和管理 Members；
- 创建和管理 Institutions；
- 创建和管理 Groups；
- 创建和管理 Accounts；
- 表达单人持有、多人共同持有和 Shared 视图；
- 为账户记录当前值；
- 支持资产和负债；
- 按成员、机构、分组、类别等维度浏览或筛选账户；
- 归档和恢复账户；
- 本地持久化；
- 账户和机构图标、图片等展示信息；
- Overview 中由后端计算资产、负债和净资产总额。

### 5.2 v0.1.2：多货币和投资组合

当前已实现的核心能力包括：

- 支持账户使用不同货币；
- 支持 Instruments；
- 支持投资账户中的 Holdings；
- 支持投资现金；
- 支持手动价格和汇率；
- 将当前现金和投资持仓转换到 Household base currency；
- 保存报价来源、时间和新鲜度等信息；
- 用户主动刷新市场报价或汇率；
- 使用可替换的 Yahoo Finance 和 Frankfurter 数据边界；
- 数据源失败时保留本地数据，并显示明确的不完整或不可用状态。

市场数据不是应用启动的前置条件。用户应该仍然可以在离线状态下查看和维护手工记录。

### 5.3 v0.1.3：家庭时间线和历史

当前已实现的核心能力包括：

- Starting point：从某个时间点开始记录家庭历史；
- Record change：用面向家庭用户的语言记录财务变化；
- 支持现金变化、资产或负债调整、转账、投资持仓变化以及 Buy/Sell 等变化类型；
- Timeline：按时间查看家庭财务变化；
- Undo：撤销已经记录的变化；
- Fix：修正已有变化；
- 历史净资产趋势；
- 历史快照和重建；
- 取消和恢复较长时间的历史计算任务。

用户不需要理解 Activity、Effect、Replay 或 Snapshot 等内部概念。界面应让用户理解“发生了什么”，而不是让用户操作内部事件模型。

### 5.4 v0.1.4：成本基础和投资收益

当前已实现的核心能力包括：

- 投资 Holding 的 average cost；
- total cost；
- unrealized gain；
- realized gain；
- 按 Instrument 和 Account 查看收益；
- 将未实现收益拆成 Instrument movement 和 currency movement；
- 按 30 天、1 年和全部时间查看 realized gain；
- 缺少当前报价或汇率时保留可用数据，并将受影响的结果标记为 Unavailable。

当前只实现 average cost，不实现 FIFO tax lots、TWR、XIRR、benchmark 或完整的家庭净资产归因桥接。设计稿不能把这些未实现概念表现成已经存在的功能。

### 5.5 v0.1.5：未来方向，尚未作为当前功能

以下方向目前只是规划，不应在“当前功能”页面中伪装成已实现能力：

- Review before post 的变化准备流程；
- 数据新鲜度提醒；
- Backup/Restore；
- Import/Export；
- 对比数据；
- 键盘优先的搜索和导航；
- 云同步、多设备同步；
- 银行、券商、钱包或交易所的直接连接；
- 后台自动刷新。

## 6. 核心业务概念

| 概念 | 用户能理解的含义 | 交互设计重点 |
| --- | --- | --- |
| Household | 整个家庭的资产负债表 | 应成为应用的主上下文，而不是隐藏在设置里的技术对象 |
| Member | 家庭中的一个人 | 用于所有权和成员视图，不等同于登录账户 |
| Institution | 银行、券商、钱包、贷款机构等 | 表示资产或负债放在哪里 |
| Group | 用户自定义的组织方式 | 例如 Emergency Fund、Retirement，不应和 Institution 混为一类 |
| Account | 一个金融容器或手工计价的资产/负债 | 普通账户应能快速创建，高级字段渐进展示 |
| Ownership | 账户由哪些成员按什么比例拥有 | 共同持有必须清楚表达，比例不能被界面四舍五入成错误结果 |
| Account Value | 某个日期的账户余额或估值 | 需要区分当前值、历史值和更新时间 |
| Instrument | 被投资的标的 | 例如股票、基金或其他投资标的 |
| Holding | 某个投资账户中持有的 Instrument 数量 | 需要关联数量、价格、货币和账户 |
| Activity | 对财务变化的用户可理解记录 | 重点是“发生了什么”，不是暴露内部事件结构 |
| Average Cost | 持仓的平均成本 | 需要和当前价值、收益清楚区分 |
| Gain | 从历史证据推导出的收益 | 需要区分已实现、未实现、标的价格变化和汇率变化 |

## 7. 当前导航与信息架构

当前 Fyne 壳层包含以下一级页面：

- Overview
- Accounts
- Investments
- Market Data
- Members
- Institutions
- Groups
- History
- Analytics
- Settings

当前代码中 Activity 作为 History 的兼容别名存在，并不是独立的一级导航页面。因此原型需要重新判断：

- Activity 是否应该成为用户看到的独立入口；
- History 是否应该包含 Timeline、净资产趋势和变化记录；
- Investments、Market Data 和 Analytics 是否应该合并成更容易理解的投资空间；
- Members、Institutions、Groups 是否适合保留为独立页面，还是应该成为 Accounts 的筛选维度；
- Settings 是否需要拆出数据管理、显示设置和市场数据设置。

设计师可以推翻当前导航结构，但必须确保核心任务的入口更容易找到，而不是为了视觉整齐而增加层级。

## 8. 需要重点设计的用户流程

### 8.1 首次进入和创建 Household

目标：用户能够理解应用是什么，并建立最小可用的家庭上下文。

建议流程：

1. 打开应用；
2. 看到产品定位和 local-first 说明；
3. 创建 Household；
4. 选择 base currency；
5. 添加至少一名 Member；
6. 进入 Overview；
7. 引导用户创建第一个 Account。

需要设计的状态：跳过、返回、校验错误、保存失败、已有数据、取消退出。

### 8.2 创建第一个 Account

目标：普通用户不需要先理解复杂的财务模型，也能完成账户创建。

需要覆盖：

- 账户名称；
- 资产或负债；
- 类别；
- 货币；
- Institution；
- Group；
- 所有成员和所有权比例；
- 初始值和日期；
- 可选图标或图片。

需要明确：哪些字段是最小必填，哪些字段可以稍后补充，哪些字段只在投资账户时出现。

### 8.3 维护账户和当前值

目标：用户可以快速更新余额，同时保留可追溯的变化历史。

需要覆盖：

- 从 Overview 或 Accounts 进入账户；
- 查看当前值、货币、所有权和更新时间；
- 更新账户值；
- 查看历史值；
- 编辑账户元数据；
- 归档账户；
- 恢复账户；
- 取消未保存修改。

### 8.4 记录一次财务变化

目标：用户用普通语言记录“发生了什么”，而不是填写内部账本结构。

原型至少需要验证：

- Starting point；
- 现金或账户值变化；
- 账户之间的转账；
- 投资持仓增加或减少；
- Buy/Sell；
- 手续费、收入或其他调整类变化；
- 变化发生日期；
- 预览后确认保存；
- 保存后查看结果。

对于复杂变化，建议采用渐进式表单或步骤式流程，而不是一开始展示所有字段。

### 8.5 查看 History 和修正记录

目标：用户可以回答“最近发生了什么”，并安全地修正错误。

需要覆盖：

- Timeline；
- 时间范围筛选；
- 账户筛选；
- 变化类型筛选；
- 查看变化详情；
- Undo；
- Fix；
- 修正前预览；
- 修正后的影响说明；
- 历史数据重新计算时的加载和取消状态。

Undo 和 Fix 是高风险交互，必须有明确的影响范围、确认语句和成功反馈。

### 8.6 查看 Investments 和 Analytics

目标：用户能够理解“现在持有什么、成本是多少、赚了或亏了多少”。

需要覆盖：

- Holding 列表；
- 数量、当前值、平均成本、总成本；
- realized gain；
- unrealized gain；
- Instrument movement；
- currency movement；
- Instrument 和 Account 维度；
- 30 天、1 年、全部时间；
- 缺少报价、缺少汇率和数据过期。

不要把 average cost、current value 和 gain 合并成一个无法解释的数字。每个指标需要有清晰名称、货币和时间语义。

### 8.7 刷新市场数据

目标：用户明确知道哪些数据会访问网络，以及刷新失败时本地数据仍然可用。

需要覆盖：

- 最近刷新时间；
- 数据来源；
- 手工报价和远程报价的区别；
- 刷新中；
- provider 失败；
- 单个 Instrument 或 FX 失败；
- 部分成功；
- 使用手工报价作为 fallback；
- 不阻止离线浏览和编辑。

### 8.8 Settings

当前 Settings 包括：

- Appearance：System、Light、Dark；
- Accent；
- Language：English、简体中文、正體中文；
- Timezone；
- First day of week；
- Date format；
- Time format；
- Display currency；
- Decimal separator；
- Grouping separator；
- Decimal places；
- FX provider 选择。

设置会自动保存。需要设计保存成功、保存失败、恢复默认值和语言切换后的反馈。

## 9. 必须覆盖的状态

每个主要页面不能只设计“有数据且操作成功”的状态。原型至少应包含：

### 数据状态

- 第一次使用，没有 Household；
- 有 Household，但没有 Account；
- 有账户，但没有历史；
- 有部分数据；
- 归档数据；
- 手工数据；
- 远程刷新数据；
- 数据过期；
- 数据不完整；
- 某个指标不可用。

### 操作状态

- 初始加载；
- 局部加载；
- 保存中；
- 保存成功；
- 保存失败；
- 网络刷新中；
- 网络刷新失败；
- 历史计算中；
- 历史计算可取消；
- Undo/Fix 确认中；
- 表单校验失败；
- 用户离开页面但有未保存输入。

### 视觉和平台状态

- Light；
- Dark；
- System；
- English；
- 简体中文；
- 正體中文；
- 窄窗口；
- 大窗口；
- 键盘操作；
- VoiceOver 或其他辅助功能。

## 10. 当前最需要解决的体验问题

以下问题是这次原型设计的重点，不要求设计师直接接受当前页面结构：

### 10.1 Overview 是否真的能回答第一问题

用户打开应用后，应该马上知道：

- 当前净资产是多少；
- 资产和负债分别是多少；
- 这个数字属于哪个 Household 和 base currency；
- 和之前相比发生了什么变化；
- 哪些数据过期或不完整。

### 10.2 账户体系是否容易理解

用户需要理解 Account、Institution、Group、Member 和 Ownership 的差异，但不应该被数据库式的层级和字段压倒。

### 10.3 简单任务和高级任务是否分层

“添加一个银行账户”和“录入一个复杂投资变化”不应该使用同样复杂的表单。建议先设计简单路径，再通过 progressive disclosure 展开高级字段。

### 10.4 当前值、历史变化和收益是否混淆

当前值回答“现在有多少”；History 回答“发生了什么”；Analytics 回答“为什么变化、赚了多少”。三者需要在导航、页面标题和指标定义上明确区分。

### 10.5 数据可信度是否被表达出来

数据来源、更新时间、手工或远程、是否完整、是否可用，都应该以简洁但明确的方式表达，不能只显示一个看起来精确的数字。

### 10.6 导航是否过于技术化

当前页面数量较多。原型应验证左侧导航、分组导航、上下文导航、页面内 Tabs 和筛选器的组合，而不是默认所有对象都必须成为一级菜单。

## 11. 本次原型建议范围

### 第一优先级

建议先完成以下完整链路：

1. 首次进入；
2. 创建 Household；
3. 创建第一个 Account；
4. Overview 查看净资产；
5. 更新账户值；
6. 查看 History；
7. 记录一条变化；
8. 查看 Investments 或 Analytics 的一个核心视图。

这些页面能够验证产品最重要的主线：

```text
建立家庭上下文 → 录入资产 → 查看当前状态 → 记录变化 → 理解变化
```

### 第二优先级

- Members；
- Institutions；
- Groups；
- 市场数据刷新；
- Settings；
- Undo/Fix 的完整交互；
- 空数据、错误和部分不可用状态。

### 暂不要求原型完整覆盖

- 云同步；
- 银行或券商直接连接；
- 自动化后台任务；
- 税务报表；
- FIFO tax lots；
- TWR/XIRR；
- 预算和日常消费记账；
- 复杂的备份恢复流程。

## 13. 交给设计师前需要确认的问题

以下问题如果还没有答案，可以在设计过程中作为待决策项，但必须显式标注，不能让设计师默默替我们决定：

1. 第一版是否只面向 macOS，还是需要同时考虑 Windows/Linux？
2. 产品默认首页是 Overview，还是 Accounts？
3. Activity 是否作为独立入口，还是属于 History？
4. Members、Institutions、Groups 是否保留为一级导航？
5. 第一版主要用户是一人家庭、夫妻，还是都需要同等支持？
6. 创建 Account 时，最少需要填写哪些字段？
7. 记录变化应该使用单页表单、步骤式流程，还是自然语言式引导？
8. “Archive” 对用户是否应该显示为“归档”，还是更容易理解的“停用”？
9. Preview、Manual、Stale、Unavailable 等状态使用什么中文表达？
10. 用户是否需要在 Overview 中看到每个数字的计算来源和明细入口？
11. 是否允许用户自定义首页卡片、指标和排序？
12. 是否需要优先支持键盘操作和 VoiceOver？

## 14. 设计评审标准

原型评审不应只看页面是否漂亮，还应检查：

- 新用户能否在几分钟内完成第一个 Account；
- 用户是否知道 Household base currency；
- 用户能否分辨当前值、历史变化和收益；
- 用户能否找到最近发生的变化；
- 用户是否知道刷新失败后哪些数据仍然可信；
- 共同所有权是否容易理解；
- 复杂投资表单是否没有压迫感；
- Undo/Fix 是否不会造成误操作；
- 无数据和异常状态是否仍然给出下一步；
- 中英文、深色模式和不同窗口尺寸下是否仍然可用。

## 15. 给设计师的简短介绍

Nestworth 是一个 local-first 的家庭财富管理工具。它不是日常记账应用，而是帮助用户建立并维护一张可信的家庭资产负债表：用户可以管理账户、成员、机构、分组、所有权、投资持仓和历史变化，并逐步理解净资产如何随着现金流、投资价格和汇率变化而变化。

这次设计的重点不是给现有页面换皮，而是重新梳理用户从“第一次进入”到“建立资产全景”，再到“持续维护并理解变化”的完整体验。请优先挑战信息架构和核心流程，再确定视觉风格。
